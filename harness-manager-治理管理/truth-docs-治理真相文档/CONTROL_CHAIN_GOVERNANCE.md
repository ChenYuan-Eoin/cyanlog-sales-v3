# 控制链治理规范

## 你现在真正关心的问题

项目从启动到后期维护，会同时存在这些东西：

- 22 万字主文档
- 后续拆出来的管理文档 / 治理文档
- AI 读取和理解的上下文面
- 实际代码与 migration
- 运行中的系统、日志、告警、报表

问题不在于“有没有这些东西”，而在于：

1. 哪一层说了算
2. 变化如何逐层传导
3. 出现不一致时谁纠正谁
4. 你不看代码，如何还能判断系统有没有跑偏

本文件就是解决这条控制链。

## 核心原则

`主文档不是日常开发真相，主文档是源头母本。`

真正可长期维护的控制链，必须从“大而全愿景”逐步收缩成“当前可执行真相”。

如果不做这层收缩，后期会发生三件事：

1. AI 每次都从 22 万字里自由发挥
2. 代码开始只服从局部实现，不再服从主文档
3. 你只能看文档和口头汇报，无法判断代码是否漂移

## 五层控制链

### L0：源头母本层

文件：

- `PROJECT-主文档.md`

职责：

- 保存完整业务蓝图
- 保存长期框架、对象全集、未来边界
- 给拆分决策提供来源

不直接承担：

- 每日开发真相
- 发布判断
- 运维判断

规则：

- L0 可以大，但不能直接指挥代码落地
- L0 中某条内容要真正生效，必须下沉到 L1 / L2

### L1：治理与模块真相层

文件示例：

- `DB_SCHEMA_GOVERNANCE.md`
- `CONFIGURATION.md`
- 本文件 `CONTROL_CHAIN_GOVERNANCE.md`

职责：

- 把 L0 的大蓝图收缩成当前阶段可执行规则
- 冻结关键决策
- 规定哪些对象先做、哪些后做、哪些先骨架化

规则：

- L1 是 AI 和开发协作的默认解释层
- L1 必须短于主文档，且必须能被维护

### L2：机器可执行真相层

文件示例：

- `schema.prisma`
- `prisma/migrations/`
- env registry
- OpenAPI / GraphQL schema
- 权限矩阵、路由白名单、配置注册表

职责：

- 让规则真正进入可执行状态
- 让 CI、脚本、审查工具能机械检查

规则：

- L2 才是发布前真正要过检的层
- L1 规则如果没有落到 L2，就还只是管理意图

### L3：实现层

内容：

- 应用代码
- 脚本
- hooks
- tests

职责：

- 按 L2 真相完成实现

规则：

- L3 不得反向定义规则
- 若代码迫使规则变化，必须回写 L1 / L2

### L4：运行证据层

内容：

- 测试结果
- migration 状态
- 审计日志
- 监控指标
- 发布记录
- 回滚记录

职责：

- 证明系统“不是看起来对，而是真的对”

规则：

- 你后期主要看 L4，而不是看代码细节

## 哪一层说了算

冲突时按下面顺序判定：

1. 已执行上线的运行证据不能被口头否定
2. L2 高于 L1
3. L1 高于 L0
4. L0 只提供来源，不直接压过当前执行真相

换句话说：

- 主文档里写了，不等于系统已经这么做
- 代码里做了，也不等于它就是对的
- 真正有效的是：L1 决策已经落入 L2，并在 L4 有证据

## AI 默认理解面怎么管

这是控制链里最关键的一环。

AI 不能每次都直接把 22 万字主文档当成当前执行真相。

默认读取顺序应当是：

1. L1 当前治理真相
2. L2 可执行真相
3. 最近变更记录
4. 必要时回溯 L0 母本

解释规则：

- 日常编码：优先读 L1 + L2
- 领域歧义：回读 L0
- 发现冲突：先报冲突，再决定回写方向

这意味着：

- 主文档继续保留长期意义
- 但 AI 的日常操作面必须是“收缩后的真相面”

## 你不看代码，怎么管理

你后期不应该被迫直接审代码。你要管理的是“证据包”。

## 变更证据包

每次重要变更都要有一份你能读懂的证据包，最低包括：

1. 这次改了什么业务决策
2. 影响哪些对象 / API / 表
3. 改了哪些 L1 文档
4. 改了哪些 L2 真相
5. 改了哪些代码路径
6. 有哪些 migration
7. 测试是否通过
8. 发布后怎么验证
9. 回滚方式是什么

你后期主要看这个，不看原始代码 diff。

## 你真正要看的四类报告

### 1. 决策冻结报告

你用来确认：

- 关键业务口径是否已冻结
- 有没有新增未决问题

### 2. 结构变更报告

你用来确认：

- 哪些表结构改了
- 为什么改
- 是否影响老数据
- 是否需要迁移 / 回滚

### 3. 发布准备报告

你用来确认：

- 当前版本能不能上
- 风险项是什么
- 哪些证据还没齐

### 4. 运行健康报告

你用来确认：

- 审核成功率
- 批注降级率
- 审批卡点
- 错误告警
- 数据漂移或权限异常

## 控制链的实际传导流程

### 流程 A：从主文档到代码

L0 主文档提出长期框架
→
L1 拆成当前阶段规则
→
L2 落成 schema / migration / contract / registry
→
L3 实现
→
L4 生成证据

### 流程 B：从运行问题回写治理

线上发现问题
→
定位到 L3 / L4 证据
→
判断是实现问题还是规则问题
→
若规则有缺口，回写 L1
→
必要时再回写 L0 母本

## 对你这个项目的具体要求

基于当前已冻结决策，控制链建议这样建：

### 主文档继续保留

`PROJECT-主文档.md` 继续作为母本，不废。

### 但日常开发不直接面对主文档全量

日常开发和 AI 协作默认只面对：

- `DB_SCHEMA_GOVERNANCE.md`
- `CONFIGURATION.md`
- 后续真实 `schema.prisma`
- migration 目录
- 需求追踪与回写机制文档

### Project / Tender 的处理方式

由于你已经明确倾向“框架一步到位”，这里采用：

- 在 L1 冻结其存在性
- 在 L2 先落骨架表
- 在 L3 不强求第一天把所有业务闭环做完

这既保住长期框架，也不把第一批实现拖死。

## 后期运维怎么判断对错

你不看代码时，最低用这三件事判断：

1. 本次变更有没有证据包
2. 运行健康报告有没有偏离阈值
3. 文档真相、执行真相、运行证据三者是否一致

只要这三者一致，后期你就不需要靠“看代码感觉”做判断。

## 后续应补的控制链资产

建议后续再补三类资产：

1. `DECISION_LEDGER.md`
   - 用来记录冻结决策和变更原因

2. `RELEASE_READINESS_REPORT.md`
   - 每次发布前 AI 自动生成，给你读

3. `RUNTIME_HEALTH_REPORT.md`
   - 定期汇总成功率、降级率、审批超时、告警

这三类文件都应该是“你能读懂的管理面”，而不是代码面。

## 一句话总结

你不是要学会看代码，你是要把系统管成：

`主文档给方向，治理文档定口径，可执行真相落工具，代码服从真相，运维只看证据。`
