# PRD文档维护规范

> 说明：本指南采用单文件维护，不再单独保留 `.toc.md` 目录副本。需要查看标题树时，直接运行目录脚本临时生成即可。

## 长期维护范围

> 约定：本项目长期维护的 Markdown 真相文档仅有 3 份。

1. `PROJECT-主文档.md`
2. `md-doc-manager-文档管理/guide-文档维护指南.md`
3. `harness-manager-治理管理/guide-harness治理指南.md`

除上述 3 份外，其他 Markdown 文档默认视为历史稿、参考稿、备份稿或冻结资产，不再作为持续维护对象。

## 设计真相（Design Truth）边界声明

本项目允许存在“设计真相层”目录用于约束 UI 视觉口径，但其定位与主文档不同：

1. `product-truth-产品真相层/design-truth-设计真相层/` 是 **视觉主题与组件语言** 的真相源（tokens + primitives），可迁移复用。
2. 该目录下的 `examples/` 仅用于预览与 sanity check，不代表产品信息架构与业务流程真相。
3. 业务流程、入口规则、模块边界、数据流转等真相仍以 `PROJECT-主文档.md` 为准。

## 冻结文档原则

1. `prd_rebuild/`、`二次文档重构/`、`历史错乱信息/` 下的 Markdown 默认视为冻结文档。
2. 各类 `.bak`、重构稿、阶段性输出稿默认视为冻结文档。
3. 冻结文档可查阅、可归档、可删除，但不应继续作为真相文档更新。

## 被管理文档配置（机器读取）

> 约定：
> 1. 机器读取“被管理文档清单”时，优先解析本章节下的第一个 `yaml` 代码块。
> 2. 该代码块负责声明“维护哪些文档”。
> 3. 运行时入口、兼容链接、hook 路径同步由 `harness-manager-治理管理/runtime-config-AI运行配置/config-配置文件/project-governance-项目治理注册表.json` 负责。

```yaml
version: 1
runtime_registry: harness-manager-治理管理/runtime-config-AI运行配置/config-配置文件/project-governance-项目治理注册表.json
managed_documents:
  - id: prd-main
    name: PROJECT-主文档.md
    path: PROJECT-主文档.md
    type: prd-main
    required: true
    maintenance_targets:
      - 保持章节编号连续且自洽
      - 保持目录与正文同步
      - 保持业务叙事、系统合约、附录边界清晰

  - id: doc-guide
    name: guide-文档维护指南.md
    path: md-doc-manager-文档管理/guide-文档维护指南.md
    type: doc-governance-guide
    required: true
    maintenance_targets:
      - 说明 PRD 文档如何被维护
      - 说明目录、编号、结构和脚本使用规则

  - id: harness-guide
    name: guide-harness治理指南.md
    path: harness-manager-治理管理/guide-harness治理指南.md
    type: harness-governance-guide
    required: true
    maintenance_targets:
      - 说明 AI 治理层如何被维护
      - 说明环境变量、hook、validator、兼容入口如何同步
```

### 文档撰写规则

1. 被纳管的主文档必须在上方配置代码块中登记。
2. 主文档的目录必须由脚本生成，不允许长期手工维护。
3. 正文中的标题层级必须稳定，至少明确到 `####`。
4. 正文不得长期混入大段实现代码，必要时应下沉到附录或治理配置中。
5. 文档中的“结束标记”只能出现在真正文件末尾。

### 文档维护规则

1. 修改 `PROJECT-主文档.md` 后，必须重新生成目录。
2. 章节或附录新增、删除、重排后，必须校验标题编号。
3. 标题不得出现在 fenced code block 内。
4. 目录、规则、脚本入口变更后，需同步更新本指南与维护配置文件。
5. 被管理文档改名或换位置后，先更新上方 `yaml` 与运行时注册表，再执行 `python3 ./scripts/sync_governance.py`。
6. **禁止随便新建文档**：补充内容时，必须先评估应归入哪个已有文档（主文档、本指南、harness治理指南）。如确实需要新建文档，必须与项目负责人确认后再执行。

## 规则分层

为避免“规则写很多但只有当前项目能用”，文档治理规则分成三层：

### A. 通用硬规则

这些规则适用于几乎所有长文档项目，应该优先脚本化，作为新项目默认规则复用：

1. 顶层标题白名单：只允许正文顶层章和附录顶层章
2. 正文章节号连续，不能跳号
3. 子标题编号必须跟随父标题编号
4. 标题编号不能重复
5. 附录开始后，禁止再出现正文顶层章节
6. 附录内部编号必须使用附录命名空间，如 `A.1`、`A.1.1`
7. fenced code block 内的示例标题不得泄漏为真实结构
8. TOC 只能脚本生成，不能长期手工维护
9. 被管理文档改名后，兼容入口必须同步

### B. 项目约定规则

这些规则适合复用，但需要按项目替换具体内容：

1. 长期维护的真相文档数量
2. 文档层 / 治理层 / 产品层 的归属边界
3. 默认主文档 ID
4. 默认附录命名方式
5. 核心对象、Agent 分类、输出物模板

### C. 人工评审规则

这些规则难以完全脚本化，但必须保留在评审清单中：

1. 用户旅程是否漂移
2. 业务入口是否被错误强制串联
3. 触发逻辑是否脱离现实
4. 产品叙事、治理规则、实现细节是否重新混杂
5. 本章是否真的符合“本章输出物”和“归属层”

## 目录同步机制

### 问题背景
PRD文档会持续增长和修订，手动维护目录行号容易出错且难以保持同步。

### 解决方案
使用自动化脚本 `./scripts/generate_toc.sh` 生成带行号的目录。

### 使用步骤

#### 1. 修改文档内容
正常编辑 `PROJECT-主文档.md`，添加/删除章节或调整内容。

#### 2. 更新目录
修改完成后，运行目录生成脚本：

```bash
./scripts/generate_toc.sh
```

或显式指定被管理文档 ID：

```bash
./scripts/generate_toc.sh prd-main
```

脚本会输出最新的目录（包含各章节的起始行号）。

#### 3. 替换目录
复制脚本输出，替换 `## 第0章：文档结构与阅读指南` 章节下代码块中的目录部分。

#### 4. 提交变更
```bash
git add PROJECT-主文档.md
git commit -m "更新第X章内容并同步目录行号"
```

## 文档结构规范

### 章节编号规则
- 一级标题：`## 第X章：章节名` （连续编号，不可跳跃）
- 二级标题：`### X.Y 小节名` （Y从0或1开始，与章号一致）
- 三级标题：`#### X.Y.Z 子小节名`
- 附录标题：`## 附录X：附录名`

### 编号一致性检查
编写新章节时，确保子标题编号与章号对应：
- 第5章的内容应为 `### 5.1`、`#### 5.1.1` 等
- 第12章的内容应为 `### 12.1`、`#### 12.1.1` 等

### 章节位置验证
新章节应放在正确的位置：
1. 第1-17章：按顺序排列
2. 附录：放在第17章之后
3. "第二部分/第三部分"等内容应归入附录或删除

## 常见维护场景

### 场景1：新增章节
1. 在正确位置插入新章节（如第18章）
2. 确保子标题编号为 `### 18.1` 等
3. 运行 `./scripts/generate_toc.sh`
4. 更新目录

### 场景2：删除章节
1. 删除章节内容
2. 重新编号后续章节（如需）
3. 运行 `./scripts/generate_toc.sh`
4. 更新目录

### 场景3：调整章节位置
1. 移动章节内容到新位置
2. 重新编号相关章节的子标题
3. 运行 `./scripts/generate_toc.sh`
4. 更新目录

### 场景4：章节内容大幅扩充/缩减
1. 修改内容（可能改变后续章节的起始行）
2. 运行 `./scripts/generate_toc.sh`
3. 更新目录（行号会变）

## 内容审查清单（P0：避免逻辑漂移）

> 目标：这份清单不是为了“写得更多”，而是为了让长文档在持续迭代下依然可读、可实现、可验证。
> 适用范围：仅对 `PROJECT-主文档.md` 的核心章节做审查（不要求覆盖全部附录）。

每次你感觉“文档又变长了/又看不懂了/又开始吵架了”，先跑一遍以下清单。

1. 入口独立性（最常见漂移源）
   - Quote / Tender / Contract / Schedule 这类入口是否被错误强制串联为“必须从报价开始”？
   - 每个入口是否都有“允许从这里开始”的明确声明（允许清单 + 禁止清单）？

2. 流程起点是否贴近真实业务
   - 是否把“合同”当成全链路起点导致前期引导失效？
   - 报价是否能独立完成（不依赖合同/招标必然存在）？

3. 触发逻辑是否现实可落地
   - “逆向时间规划/日程规划”是否依赖一个现实中还不存在的确定交付日期？
   - 是否把业务上“可配置/可选择”的行为写死为后台模板强制执行？

4. 数据流与状态机是否自洽（从“功能列表”转向“电路/数据流”也必须可读）
   - 核心对象（Quote/Tender/Contract/Schedule/Config/Knowledge）的状态流转是否有全景图？
   - 外部系统（CRM/邮箱/文件系统/IM/日历等）的输入输出边界是否清楚？
   - 事件驱动/降级链路是否写成“可配置策略”，而不是“只能这样做”？

5. Agent 分层是否被污染（产品 Agent / 开发 Agent / 治理 Agent）
   - 产品 Agent：只描述输入/输出/边界/降级/指标，不落实现代码。
   - 开发 Agent：只描述开发期如何辅助（review/test/doc-sync），不混入产品功能叙事。
   - 治理/监控 Agent：只描述监控、回放、故障定位、隔离策略，不混入具体业务流程。

6. 章节“输出物”是否兑现
   - 每章开头的“本章输出物”是否真的在章内产出（图/表/合约/状态机/配置项）？
   - 若本章只是讨论与推演，是否被明确标为“讨论稿/假设/待验证”？

7. PRD 对开发者是否仍有意义
   - 文档是否能直接回答：数据从哪里来、到哪里去、触发什么动作、失败时怎么降级、如何观测？
   - 如果把实现细节删掉，业务逻辑是否仍然完整可执行？


## 脚本说明

### generate_toc.sh
通过注册表解析目标文档，提取所有章节标题及其行号，生成格式化的目录。

**输出格式**：
```
87    第1章：业务地图全景
585   第2章：核心业务链路
...
```

**使用示例**：
```bash
# 生成当前目录
./scripts/generate_toc.sh

# 按文档 ID 生成目录
./scripts/generate_toc.sh prd-main

# 重命名或迁移后同步兼容入口
python3 ./scripts/sync_governance.py
```
