# Price-v3 身份与权限目标蓝图

- 状态：目标设计，不代表已实现
- 当前执行：`WP50` 统一飞书与纷享的连接记录、加密状态、草稿/生效版本和通讯录只读预览
- 当前 Next：`WP92` 在 WP50 基础上完成目录差异预览、主来源切换和原子回滚；通过后再联合复验 `WP94` 双登录路径
- 未关闭责任包：`WP82` 承载租户初始化、Owner、默认角色、角色委托和数据范围，不能因 WP50 通过而关闭
- 唯一数据库：`cyanlog-sales-v3`

## 1. 结论

采用“不可变主体根 + 稳定外部映射 + 租户成员关系 + 原子权限 + 角色 + 数据范围 + 审计”的目标，但不照搬新表名，也不在运行时动态改写 SQL。

现有表继续作为真相源：

| 目标概念 | 现有实体 |
| --- | --- |
| 租户 | `organizations` |
| 租户成员 | `user_organizations` |
| 主体 | `users` |
| 外部身份边 | `external_identities` |
| 外部来源 | `organization_sources` |
| 原子权限 | `permission_points` |
| 角色 | `roles` 与其租户权限覆盖 |
| 角色授予 | `user_roles` |
| 手机号历史 | `phone_history` |

不为命名统一而重命名全部 `org_id/system_org_id`。产品文案统一称“租户”，数据库在一轮可控迁移前继续使用 `org_id`。

## 2. 身份与认证

### 2.1 主体

- `users.id` UUID 是唯一主体根。
- 权限、业务外键、审计、工单归属只引用 UUID。
- `display_name` 和 `phone` 只展示，不承担授权关系。
- Price-v3 先按“全局 person + 组织成员关系”演进，`users.org_id` 作为兼容默认组织字段，不再作为跨租户身份真相。

### 2.2 外部身份

- `(organization_sources.system_org_id, provider, external_user_id)` 是稳定外部身份。
- 同一来源下 `external_user_id` 只能对应一个 `canonical_user_id`。
- 同一来源下 `canonical_user_id` 只能有一条 `matched` 映射。
- 已存在映射但本次 subject 不同：拒绝并转人工，不按手机号覆盖。
- `openUserId`、手机号、姓名都不能与 `users.employee_id` 自动等值关联。

### 2.3 首次绑定与账号接管防护

- provider 返回手机号只称为“provider 返回手机号”，不宣称由纷享独立验证。
- 没有稳定映射时，SSO 默认 fail-closed。
- 禁止仅凭手机号静默写映射并登录。
- 可用受审计的 step-up 路径：
  1. 管理员预先建立 `matched` 映射；
  2. 一次性绑定码；
  3. 短信验证码；
  4. 其他企业身份二次确认。
- 最终选择需单独验收并明确费用。持续付费短信服务不是默认前提。

### 2.4 手机号历史

- 当前手机号在同一作用域内唯一。
- `phone_history` 使用 PostgreSQL 排他约束禁止同号时间区间重叠。
- 历史业务通过当时的 `user_id` 追溯，不用当前手机号回推。

### 2.5 重复账号合并

- 主账号优先是全体员工账号的固定运营规则，不允许为单个账号写一次性手工改库例外。
- 主账号由系统配置的权威绑定源决定：`organization_sources.status='active'` 且 `authority_scope.identity='authoritative'`，权威来源的稳定 subject 映射到哪个 `users.id`，哪个账号就是该自然人的主账号。绑定源配置和有效映射是身份权威，权限角色、展示名称、业务引用数量均不能反向定义主账号。
- 权威来源缺少一对一稳定映射，或同一自然人存在多个冲突映射时必须失败关闭；操作员不能通过 `SUPER_ADMIN` 身份或引用数量“选一个看起来更像主账号”的 UUID。
- 合并保留主账号 UUID、资料、会话和稳定映射，合并来源账号独有的部门与角色，并把受外键约束的业务引用迁入主账号。
- 同一来源在主账号与来源账号均已存在 `matched` 映射时失败关闭；必须人工核对后再处理，不能覆盖 `openUserId`。
- 来源账号会话立即撤销；来源账号的来源行、组织关系与历史事件保留为停用记录，可变手机号和员工号清空，并写入前后状态审计。
- 合并使用服务端事务命令 `admin_merge_duplicate_identity_v1`。这里的 `SUPER_ADMIN` 只是执行操作的权限门禁，不是主账号判据；来源账号永不重新获得登录能力。

## 3. 三种正交概念

以下概念不可混用：

| 层 | 回答的问题 | 当前/目标实体 | 不能拿来做什么 |
| --- | --- | --- | --- |
| 身份 | 这个自然人是谁，哪个 UUID 是唯一根 | 权威绑定源、`external_identities`、`users.id` | 不能用角色、姓名、手机号或业务引用数量定义主账号 |
| 权限角色 | 这个账号能否使用平台功能/管理入口 | `roles`、`user_roles`、权限点，`SUPER_ADMIN/ADMIN/...` | 不能定义自然人身份、账号主次或业务对象责任人 |
| 系统业务角色 | 这个人在业务对象“系统”中承担什么业务责任 | 未来独立业务对象角色，完全脱离 RBAC | 不能写入 `roles.code`、`user_roles` 或复用权限点；不在 WP94 实现 |

“系统超管”是现有权限角色的展示/管理语义，不是用户名，也不是主账号类型。未来的“系统角色”服务于业务对象，即使中文名称相近，也与这里的系统管理权限角色无关。

## 4. 租户与 Owner

目标字段：

```text
organizations.owner_user_id UUID NOT NULL
```

约束：

- 每个租户恰好一个 Owner。
- Owner 必须是该租户活跃成员。
- Owner 转移只能由当前 Owner 发起，并在单事务内完成。
- 非 Owner 不得删除或降级 Owner 的系统管理角色。
- Owner 不得撤销自己的 Owner 锚点。
- 被拒绝的 Owner 操作必须在独立审计路径中留痕。

实现边界：

- 现阶段没有租户创建入口，因此不在 `WP94` 增加“按已有租户授予超管”的临时 bootstrap 页面。
- 系统级 bootstrap 只允许在系统尚无租户时运行，不适用于已有企业。

## 5. 权限模型

### 5.1 平台根角色与租户管理角色分离

当前 `SUPER_ADMIN` 带 `*`，不能直接当作租户内可多实例管理员复用。

目标语义：

- `PLATFORM_ADMIN`：极少数平台运维身份，不能由租户自行授予。
- `TENANT_ADMIN`：租户管理身份，可多个，受权限子集和 Owner 约束。
- `EMPLOYEE`：成员基线角色。
- 业务职位（GM、TL、财务主管、销售经理）不新增为系统管理角色；使用部门、岗位和数据范围表达。

从现有 `SUPER_ADMIN` 迁出需要独立的 `WP82` 数据迁移与回归，不能在 SSO 批次中顺手改名。

### 5.2 原子权限

- 继续使用 `permission_points` 作为稳定权限目录。
- 保持现有 `resource:action` 编码，不批量改成 `domain.resource.action`；如需要命名空间，新增结构化列，不破坏历史授权。
- 原子权限由迁移/代码发布维护，租户只能选择，不能发明。

### 5.3 角色

- 系统角色带 `is_system` 和稳定模板标识，租户不能删除核心模板。
- 租户自定义角色只能从系统模板派生或按权限子集创建。
- 不复制一套 `roles` 模板表和实例表；优先在现有 `roles` 增加租户归属与系统锁定元数据。
- 角色修改必须单调推进授权版本或更新时间，但不能依赖长期缓存保存权限真相。

### 5.4 委托规则

授予者有效权限集合必须包含被授予角色权限集合：

```text
Permissions(target_role) subset-of Permissions(actor)
```

另加两条硬约束：

- 非 Owner 不得修改 Owner。
- 操作者不得通过同一事务移除自己的最后管理权限。

不把 GM/TL/EMPLOYEE 硬编码成一条不可扩展的角色继承链。

## 6. 数据范围

功能权限回答“能不能做”，数据范围回答“能对哪些行做”。

建议范围：

- `self`
- `team`
- `department_tree`
- `organization`
- 显式资源授权

运行时约束：

- 每个受保护查询同时应用 `system_org_id/org_id` 与数据范围谓词。
- 服务端路由必须从数据库当前成员状态解析租户，不接受浏览器自选租户。
- 继续使用显式、参数化的查询构造器；不引入不可审计的动态 SQL 字符串改写。
- RLS 作为纵深防御，但不替代服务端资源归属检查。

## 7. 登录与请求门禁

登录必须同时满足：

1. OAuth state、企业 subject 和系统会话校验通过；
2. 稳定外部映射命中 `users.id`；
3. 用户是该租户有效成员；
4. 用户至少有一个有效角色；
5. 角色权限可在当前请求新鲜解析。

以下情况必须拒绝：

- 无映射或映射冲突；
- 停用、离职或跨租户；
- 有效成员但零角色；
- 浏览器伪造用户、租户、角色或权限头。

## 8. 失效与审计

- 当前中间件每请求读取数据库授权上下文，因此本阶段不需要再叠加 Redis 权限缓存和 `role_version`。
- 若未来引入缓存，版本号只用于缓存失效，不替代数据库真相。
- 成功和拒绝都记录：actor、target、tenant、action、resource、scope、result、reason、request_id、时间。
- 数据库事务内拒绝通常随异常回滚；拒绝审计由服务端在事务失败后独立写入，避免丢失。
