## 1. 结论

采用“不可变主体根 + 稳定外部映射 + 租户成员关系 + 原子权限 + 角色 + 数据范围 + 审计”的目标，但不照搬新表名，也不在运行时动态改写 SQL。

现有表继续作为真相源：

| 目标概念 | 现有实体 |
| --- | --- |
| 租户 | `organizations` |
| 租户成员 | `user_organizations` |
| 主体 | `users` |
| 外部身份边 | `external_identities` |
| 外部来源 | `organization_sources` |
| 原子权限 | `permission_points` |
| 角色 | `roles` 与其租户权限覆盖 |
| 角色授予 | `user_roles` |
| 手机号历史 | `phone_history` |
| 雇佣历史 | `personnel_employment_periods` |
| 邀请 | `personnel_invitations` |
| 目录差异与应用记录 | `organization_directory_cutover_plans`、`organization_directory_cutover_runs` |

不为命名统一而重命名全部 `org_id/system_org_id`。产品文案统一称“租户”，数据库在一轮可控迁移前继续使用 `org_id`。

`organization_sources` 是数据面的提供方连接记录，不是“所有身份数据一张表”。每个系统组织、每个提供方只有一条连接记录，保存提供方类型、外部企业标识、加密的草稿/生效凭据、连接 revision、连接状态、权威范围和生命周期审计。连接、目录范围、企业登录等能力声明来自代码注册表并在每次读取时派生；数据库不应复制一组可能与适配器不一致的能力布尔值。部门、自然人、组织成员、部门关系、外部身份和邀请仍按各自事实拆表；这样才能在连接切换、离职、多组织成员关系和身份冲突时保持可追溯。

提供方差异放在无状态代码适配器中，而不是数据库分支条件。这里的“适配器”不是一个承载全部能力的巨型 `ProviderAdapter`，而是一组独立能力合同的注册组合；连接记录仍是唯一数据锚点，提供方可以只实现当前具备的能力，不能用一个布尔值把目录同步和企业登录一起视为可用。

### 1.1 数据面与适配器面

| 层次 | 责任 | 禁止越界 |
| --- | --- | --- |
| 连接数据面 | `organization_sources` 每个系统组织、每个提供方一条记录，保存外部企业标识、加密凭据、revision、能力状态与审计 | 不保存人员、部门、角色或业务权限真相 |
| 连接适配器 | 解析和校验提供方凭据，验证应用/企业身份，返回稳定外部企业标识和能力矩阵 | 不写数据库，不自行启用来源或切换权威 |
| 目录适配器 | 读取授权范围内的部门与员工快照，并独立返回范围证明、结构完整性、告警、稳定外部主键和显式主属部门 | 不直接 upsert，不按姓名或手机号合并，不把“分页读完”冒充“全公司已读完”，不按部门数组顺序猜主属关系 |
| 企业登录适配器 | 生成授权请求、校验回调、交换 token、规范化提供方稳定 subject，并校验企业标识 | 不创建 `users`、成员、角色或寄件许可，不选择系统组织，不签发业务权限 |
| 提供方中立服务 | 连接生命周期、不可变差异计划、原子应用/回滚、身份映射解析、会话签发和业务授权 | 不包含 `if provider === ...` 的组织写分支 |

当前代码已将能力拆成三个注册面：`OrganizationConnectionAdapter` 只处理凭据 schema、加密前校验、企业连接验证和存储校验；`DirectoryAdapter` 只读取授权目录、归一提供方状态并给出显式主属部门；`EnterpriseLoginAdapter` 只处理授权 URL、提供方拒绝、code 交换和企业 subject。提供方中立的目录服务负责范围证明之后的快照、差异、应用和回滚。纷享实现连接、目录和登录三项能力；飞书实现连接和目录，但当前没有企业登录适配器，因此 `ssoAvailable=false`。纷享现有回调路由仍需在 WP94 改为消费登录注册表并完成中性身份/会话服务与真实登录证据，因此当前只能表述为适配器代码已就绪，不能表述为多提供方企业登录已经生产接通。

当前能力矩阵由注册表派生，不由 UI 猜测：

| 提供方 | 凭据验证 | 目录预览 | 独立目录范围证明 | 企业登录 |
| --- | --- | --- | --- | --- |
| 纷享销客 | 已实现 | 已实现 | 尚未实现，当前 `scopeVerified=false` | 适配器已实现，生产登录未验收 |
| 飞书 | 已实现 | 已实现 | 尚未实现 | 未实现，必须失败关闭 |
| 企业微信 / 钉钉 | 未实现 | 未实现 | 未实现 | 未实现 |

这些是代码能力，不是租户连接状态。某个能力“已实现”仍不代表当前租户已验证、已启用或已有生产证据。

适配器注册必须分别声明能力，例如 `credentialVerification`、`directoryPreview`、`directoryScopeProof`、`enterpriseLogin`。UI、API 和调度只消费能力声明，不按提供方名称猜实现。未实现的能力必须失败关闭；外部 OAuth 回调只能从服务端已保存的连接和一次性 state 解析目标组织，不能相信浏览器回传的 `org_id`。

### 1.2 新增提供方的实现边界

采用“一个运行时模型 + 能力插件”，不采用一个同时承担 OAuth、通讯录、组织和会话写入的巨型 `ProviderAdapter`：

| 扩展点 | 提供方需要实现的内容 | 共享代码保留的责任 |
| --- | --- | --- |
| Provider 目录项 | 稳定 `key`、显示名和未接入原因 | 统一生成前台来源卡片与能力矩阵 |
| `OrganizationConnectionAdapter` | 凭据字段、输入 schema、企业身份验证、旧凭据解密规则 | `organization_sources` 草稿/生效版本、加密、审计、晋升和回滚 |
| `DirectoryAdapter` | 分页读取、提供方状态归一、稳定外部 ID、主属部门与范围证据 | 不可变快照、身份候选、差异计划、原子应用和回滚 |
| `EnterpriseLoginAdapter` | 授权 URL、回调校验、code 换取、稳定 subject，并把提供方协议中的企业标识校验完成后归一为连接记录的企业键 | state、一次性消费、身份映射、成员/角色校验和系统会话 |

新增飞书、企微、钉钉或其他提供方时，必须新增或替换 Provider 实现并在注册表登记；不得在 `service.ts`、目录切源服务或 UI 中按提供方名称增加业务分支。提供方可以只实现其中一部分能力，未实现部分必须显示为未接入并拒绝调用。连接凭据最终仍写入同一张 `organization_sources`，只在适配器内部处理字段格式、签名方式、分页协议和 token 交换差异。

粘贴方案确实包含 `ProviderAdapter`，这一点不能遗漏；争议只在合同粒度。单列 `ProviderAdapter` 可以作为概念起点，但不足以表达能力错位：企业应用凭据验证成功不等于目录全量可读，目录可读不等于目录权威，拥有外部账号也不等于系统成员或寄件许可。因此当前实现保留提供方适配器，同时拆成三个独立能力合同，并用同一个 Provider 目录项关联。

补全方案的实体全集可以采纳，但必须按现有真相源落地，并做三点修正：

1. 保留 `users`、`organizations`、`departments`、`user_organizations`、`user_departments`、`external_identities`、`personnel_invitations` 等独立事实表；`organization_sources` 只保存连接，不把人员、部门、角色或 OAuth 会话塞入同一张表。
2. `external_identities` 绑定 `users.id`，组织成员关系单独用 `user_organizations` 表达；外部身份不能绑定会在离职、重入或切换组织时结束并重建的 `membership_id`。
3. Provider 差异只进入无状态适配器。连接、目录和企业登录是三个独立注册面；共享身份服务只接受“已校验的稳定 subject + 与连接记录一致的企业键”，再执行身份映射、成员/角色检查与会话签发，不出现按 provider 名称分支的业务写入。

提供方可能存在多种企业标识。例如纷享连接记录使用 EA，而 OAuth 授权码响应还包含 corpId。适配器必须先证明二者属于同一已保存企业，再向共享服务返回 `organization_sources.external_tenant_id` 对应的统一企业键；不能让共享服务直接比较两个名字相同但语义不同的协议字段。

### 1.3 重构决策与触发条件

本轮不是“永久不重构”，也不是用重构替代业务交付。现有证据如下：

| 评估项 | 当前证据 | 结论 |
| --- | --- | --- |
| 身份真相 | `users`、`user_organizations`、`departments`、`user_departments`、`external_identities`、`personnel_invitations` 已分别承载主要事实 | 语义基本对齐，直接推翻会增加外键、RLS 和历史数据迁移风险 |
| 提供方差异 | 连接、目录、企业登录已有三个无状态注册面，共享服务不按 Provider 写业务分支 | 新增能力可在现有边界内补强 |
| 目录切源 | 已有不可变计划、显式应用、回读和回滚的运行合同 | 应补齐真实 Provider 契约，不用新框架替代已有合同 |
| 当前真实缺陷 | 纷享主属部门字段解析错误、目录范围未证明、旧直写路由需退役、部分 Provider 能力未实现 | 根因位于适配器契约和能力门禁，不是核心身份模型无解 |
| 当前迁移收益 | 改名或重建表不会直接改善目录读取、SSO 或寄件许可；却会同时影响认证、RLS、历史外键和回滚 | 本批不做迁移式重构 |

因此本批采用“保留核心真相表 + 修正 Provider 协议 + 收紧能力门禁 + 补真实证据”的局部演进。任何代码或文档都不能把“分页读完”直接写成“目录范围已证明”，也不能因适配器代码存在就写成“生产已接通”。

以下任一证据出现时，必须停止局部打补丁，单独立项做有迁移计划的重构：

1. 需要在同一组织对部门树、成员或身份做分段、双权威或时间窗授权，而现有单一权威来源合同无法表达。
2. 同一自然人在同一组织需要同时存在多个可登录身份档案，且这些档案拥有不同角色或寄件许可；现有用户根加成员关系已无法表达。
3. `users.org_id` 以外的多组织上下文进入认证或 RLS，现有兼容默认组织字段导致跨租户查询，无法通过局部隔离消除。
4. 连续新增两个 Provider 都迫使修改共享连接、目录切源或会话服务的数据分支，说明适配器边界失真。
5. 原子切源需要比现有“整批计划、确认、应用、回读、回滚”更细的事务协议，现有 RPC 与审计表无法安全承载。
6. 生产证据证明现有外部身份唯一约束会导致错绑、重入丢失或历史归属破坏，且不能通过迁移前后对账修复。
7. 认证、权限或数据隔离发生事故，证据表明根因是核心模型而不是某个 Provider 的读取或校验缺陷。

未来触发重构时，迁移方案也必须同时给出：事实表兼容映射、历史外键与 RLS 影响、双写或影子读取策略、全量对账、灰度与回滚、以及切换前后的生产用户路径证据。重构本身不是完成标志，只有业务能力达到验收状态才算完成。

## 2. 身份与认证

### 2.1 主体

- `users.id` UUID 是唯一主体根。
- 权限、业务外键、审计、工单归属只引用 UUID。
- `display_name` 和 `phone` 只展示，不承担授权关系。
- Price-v3 先按“全局 person + 组织成员关系”演进，`users.org_id` 作为兼容默认组织字段，不再作为跨租户身份真相。

### 2.2 外部身份

- `(source_id, external_user_id)` 是稳定外部身份；`source_id` 唯一解析到一条 `(system_org_id, provider)` 连接记录。
- `external_identities.system_org_id` 必须与连接记录的 `system_org_id` 一致，并提供方类型以连接记录为准，不把浏览器或回调参数作为来源真相。
- 同一来源下 `external_user_id` 只能对应一个 `canonical_user_id`。
- 同一来源下 `canonical_user_id` 只能有一条 `matched` 映射。
- 已存在映射但本次 subject 不同：拒绝并转人工，不按手机号覆盖。
- `openUserId`、手机号、姓名都不能与 `users.employee_id` 自动等值关联。

外部身份的主映射保持到 `canonical_user_id`，并由 `system_org_id` 限定企业；登录时再解析该用户在目标组织的当前有效 `user_organizations` 成员关系。不要把 `membership_id` 设为唯一身份锚点：同一自然人在一个组织可能有多个连续雇佣周期，成员关系会结束和重建，而身份映射与历史业务 UUID 必须保持稳定。若未来一个人可在同一组织同时拥有多个可登录成员身份，必须另建明确的 profile/employment 模型并单独评审，不能用当前字段猜测。

因此，“全局用户 + 组织 + 部门树 + 成员关系 + 外部身份 + 邀请”是合理的实体全集，但不能把外部身份挂到成员关系上。推荐关系为：外部身份 `(source_id, external_user_id) → users.id`；成员关系 `users.id × organizations.id`；部门关系再挂到成员关系；邀请是独立、可过期、需接受的凭据。邮箱、手机号和姓名只作为候选匹配证据，不能作为全局自动合并键。邀请接受、管理员手工绑定和登录时身份解析是三条有审计的流程，OAuth 回调不能替代其中任何审批。

### 2.2.1 目录人员与登录账号

目录中的“员工”与“可登录账号”是两个状态。目录同步可以形成组织成员候选或待认领成员资料，但只有满足身份映射、成员状态、角色和登录许可后才能登录。SSO 回调不得因为外部用户存在就 JIT 创建 `users`、成员资格、角色或寄件许可。

如果产品要求首次同步即展示全部员工，后续必须有独立的、提供方中立的目录预置规则：创建带 `source=provider`、`login_enabled=false` 且无角色的待认领记录，并记录来源与快照；管理员审核或邀请后再形成可登录账号。该预置规则属于 WP93 的成员与许可范围内独立实现，不能混入 WP92 的身份匹配或 WP94 的登录回调，也不能把“建了人员行”表述成“已有可用账号”。

### 2.3 首次绑定与账号接管防护

- provider 返回手机号只称为“provider 返回手机号”，不宣称由纷享独立验证。
- 没有稳定映射时，SSO 默认 fail-closed。
- 禁止仅凭手机号静默写映射并登录。
- 可用受审计的 step-up 路径：
  1. 管理员预先建立 `matched` 映射；
  2. 一次性绑定码；
  3. 短信验证码；
  4. 其他企业身份二次确认。
- 最终选择需单独验收并明确费用。持续付费短信服务不是默认前提。

### 2.4 手机号历史

- 当前手机号在同一作用域内唯一。
- `phone_history` 使用 PostgreSQL 排他约束禁止同号时间区间重叠。
- 历史业务通过当时的 `user_id` 追溯，不用当前手机号回推。

### 2.5 重复账号合并

- 主账号优先是全体员工账号的固定运营规则，不允许为单个账号写一次性手工改库例外。
- 主账号由系统配置的权威绑定源决定：`organization_sources.status='active'` 且 `authority_scope.identity='authoritative'`，权威来源的稳定 subject 映射到哪个 `users.id`，哪个账号就是该自然人的主账号。绑定源配置和有效映射是身份权威，权限角色、展示名称、业务引用数量均不能反向定义主账号。
- 权威来源缺少一对一稳定映射，或同一自然人存在多个冲突映射时必须失败关闭；操作员不能通过 `SUPER_ADMIN` 身份或引用数量“选一个看起来更像主账号”的 UUID。
- 合并保留主账号 UUID、资料、会话和稳定映射，合并来源账号独有的部门与角色，并把受外键约束的业务引用迁入主账号。
- 同一来源在主账号与来源账号均已存在 `matched` 映射时失败关闭；必须人工核对后再处理，不能覆盖 `openUserId`。
- 来源账号会话立即撤销；来源账号的来源行、组织关系与历史事件保留为停用记录，可变手机号和员工号清空，并写入前后状态审计。
- 合并使用服务端事务命令 `admin_merge_duplicate_identity_v1`。这里的 `SUPER_ADMIN` 只是执行操作的权限门禁，不是主账号判据；来源账号永不重新获得登录能力。

## 3. 三种正交概念

以下概念不可混用：

| 层 | 回答的问题 | 当前/目标实体 | 不能拿来做什么 |
| --- | --- | --- | --- |
| 身份 | 这个自然人是谁，哪个 UUID 是唯一根 | 权威绑定源、`external_identities`、`users.id` | 不能用角色、姓名、手机号或业务引用数量定义主账号 |
| 权限角色 | 这个账号能否使用平台功能/管理入口 | `roles`、`user_roles`、权限点，`SUPER_ADMIN/ADMIN/...` | 不能定义自然人身份、账号主次或业务对象责任人 |
| 系统业务角色 | 这个人在业务对象“系统”中承担什么业务责任 | 未来独立业务对象角色，完全脱离 RBAC | 不能写入 `roles.code`、`user_roles` 或复用权限点；不在 WP94 实现 |

### 3.1 外部组织接入的五项独立能力

外部组织接入只有一张提供方连接记录，但必须有五项独立状态和证据。任何一项成功都不能自动推导另一项成功：

| 能力 | 回答的问题 | 成功证据 | 不能替代 |
| --- | --- | --- | --- |
| 连接凭据 | 系统能否认证到正确企业应用 | 企业标识、凭据版本、连接验证和回读 | 目录全量范围、目录权威、SSO |
| 目录可读范围 | 应用员工能否读取全公司目录 | 管理员权限或组织总数对账等服务端证明 | 分页结束、结构自洽、连接已验证 |
| 目录权威 | 当前是否以该来源形成有效部门与成员关系 | 不可变差异计划、显式确认、事务应用和回读 | 企业登录、身份映射、寄件许可 |
| 企业 SSO | 是否允许该提供方作为企业登录协议 | `ssoAvailable`、active 来源、显式 `authority_scope.identity=authoritative` | 目录主来源、成员已有、角色已有 |
| 身份映射与业务授权 | 外部自然人映射到哪个 UUID，能做什么 | 唯一 `external_identities → users.id`、成员状态、新鲜角色、数据范围 | 目录成员数、姓名/手机号、CRM 员工 ID |

目录变更固定按 `范围证明 → 不可变快照 → 差异计划 → 显式确认 → 原子应用 → 验证 → 原子回滚` 执行。`complete=true` 只表示已返回范围内部关系自洽；`scopeVerified=true` 才表示能证明该范围就是全公司目录。SSO 只认证稳定 subject 并解析既有映射，不创建成员、不切换目录权威、不授予寄件权限。

所有提供方的目录写入只能进入同一个提供方中立的计划、应用和回滚服务。历史飞书直写接口 `/api/access/feishu/sync` 已停用为迁移提示；任何提供方都不得保留先写部门、失败后返回“部分完成”的第二条写入链。

管理界面中的 `组织架构` 只展示系统有效组织结果；连接凭据、目录读取范围、目录主来源、企业 SSO、身份映射与寄件授权五种控制全部放在 `外部系统接入`，并分行展示，避免把一次连接保存或一次目录同步误读为整个企业接入完成。

“系统超管”是现有权限角色的展示/管理语义，不是用户名，也不是主账号类型。未来的“系统角色”服务于业务对象，即使中文名称相近，也与这里的系统管理权限角色无关。

## 4. 租户与 Owner

目标字段：

```text
organizations.owner_user_id UUID NOT NULL
```

约束：

- 每个租户恰好一个 Owner。
- Owner 必须是该租户活跃成员。
- Owner 转移只能由当前 Owner 发起，并在单事务内完成。
- 非 Owner 不得删除或降级 Owner 的系统管理角色。
- Owner 不得撤销自己的 Owner 锚点。
- 被拒绝的 Owner 操作必须在独立审计路径中留痕。

实现边界：

- 现阶段没有租户创建入口，因此不在 `WP94` 增加“按已有租户授予超管”的临时 bootstrap 页面。
- 系统级 bootstrap 只允许在系统尚无租户时运行，不适用于已有企业。

## 5. 权限模型

### 5.1 平台根角色与租户管理角色分离

当前 `SUPER_ADMIN` 带 `*`，不能直接当作租户内可多实例管理员复用。

目标语义：

- `PLATFORM_ADMIN`：极少数平台运维身份，不能由租户自行授予。
- `TENANT_ADMIN`：租户管理身份，可多个，受权限子集和 Owner 约束。
- `EMPLOYEE`：成员基线角色。
- 业务职位（GM、TL、财务主管、销售经理）不新增为系统管理角色；使用部门、岗位和数据范围表达。

从现有 `SUPER_ADMIN` 迁出需要独立的 `WP82` 数据迁移与回归，不能在 SSO 批次中顺手改名。

### 5.2 原子权限

- 继续使用 `permission_points` 作为稳定权限目录。
- 保持现有 `resource:action` 编码，不批量改成 `domain.resource.action`；如需要命名空间，新增结构化列，不破坏历史授权。
- 原子权限由迁移/代码发布维护，租户只能选择，不能发明。

### 5.3 角色

- 系统角色带 `is_system` 和稳定模板标识，租户不能删除核心模板。
- 租户自定义角色只能从系统模板派生或按权限子集创建。
- 不复制一套 `roles` 模板表和实例表；优先在现有 `roles` 增加租户归属与系统锁定元数据。
- 角色修改必须单调推进授权版本或更新时间，但不能依赖长期缓存保存权限真相。

### 5.4 委托规则

授予者有效权限集合必须包含被授予角色权限集合：

```text
Permissions(target_role) subset-of Permissions(actor)
```

另加两条硬约束：

- 非 Owner 不得修改 Owner。
- 操作者不得通过同一事务移除自己的最后管理权限。

不把 GM/TL/EMPLOYEE 硬编码成一条不可扩展的角色继承链。

## 6. 数据范围

功能权限回答“能不能做”，数据范围回答“能对哪些行做”。

建议范围：

- `self`
- `team`
- `department_tree`
- `organization`
- 显式资源授权

运行时约束：

- 每个受保护查询同时应用 `system_org_id/org_id` 与数据范围谓词。
- 服务端路由必须从数据库当前成员状态解析租户，不接受浏览器自选租户。
- 继续使用显式、参数化的查询构造器；不引入不可审计的动态 SQL 字符串改写。
- RLS 作为纵深防御，但不替代服务端资源归属检查。

## 7. 登录与请求门禁

登录必须同时满足：

1. OAuth state、企业 subject 和系统会话校验通过；
2. 稳定外部映射命中 `users.id`；
3. 用户是该租户有效成员；
4. 用户至少有一个有效角色；
5. 角色权限可在当前请求新鲜解析。

以下情况必须拒绝：

- 无映射或映射冲突；
- 停用、离职或跨租户；
- 有效成员但零角色；
- 浏览器伪造用户、租户、角色或权限头。

## 8. 失效与审计

- 当前中间件每请求读取数据库授权上下文，因此本阶段不需要再叠加 Redis 权限缓存和 `role_version`。
- 若未来引入缓存，版本号只用于缓存失效，不替代数据库真相。
- 成功和拒绝都记录：actor、target、tenant、action、resource、scope、result、reason、request_id、时间。
- 数据库事务内拒绝通常随异常回滚；拒绝审计由服务端在事务失败后独立写入，避免丢失。
