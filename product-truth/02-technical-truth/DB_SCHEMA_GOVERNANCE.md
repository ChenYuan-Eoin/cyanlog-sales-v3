# 数据库表结构治理规范

## 当前状态

当前工作区的活动业务仓是 `product-truth/product-code`。截至 2026-05-30，现状如下：

- 业务仓内还没有 `prisma/schema.prisma`
- 业务仓内还没有正式的 migration 目录
- `PROJECT-主文档.md` 中大量 Prisma / SQL / Schema 片段仍属于设计材料，不是可执行真相

结论：当前数据库治理仍停留在“文档有口径，但运行代码没有可执行真相入口”的阶段。

## 当前已冻结决策

以下决策已在 2026-05-30 冻结，后续 schema 设计默认按此执行，除非显式变更本文件。

1. 租户策略：`V1 单租户 + 多组织`
2. `Project / Tender`：进入初始长期框架，但第一批只做骨架表，不做一次性大而全展开
3. 报价模型：必须版本可追溯
4. 合同审核：采用 run 模型
5. 文件治理：建立统一 `file_objects` 表
6. 审批治理：采用通用 `approval_requests + approval_steps` 路径，第一批先服务报价审批

补充解释：

- `单租户 + 多组织` 的意思是：V1 默认服务一家公司内部，不按 SaaS 多企业隔离来建；但公司内部部门、区域、岗位树必须是正式模型。
- `Project / Tender` 进入初始框架，不等于第一天把所有细节建完；正确做法是先把稳定主干落下，再围绕真实流程逐步充实。

## 适用范围

本规范约束以下内容：

- PostgreSQL / Supabase 表、列、索引、约束、外键
- 视图、触发器、RLS 策略
- 迁移脚本、回填脚本、回滚策略
- 后端 PR 中所有表结构变更

本规范不直接约束：

- Redis key 设计
- MinIO bucket 命名
- 前端本地缓存结构

## 核心判断

静态文档不够。只要后端开始真实建表，本项目就必须切到“动态治理”。

这里说的动态治理，至少包括：

1. 有唯一的可执行 schema 真相入口
2. 有版本化 migration 目录
3. 有 CI 校验
4. 有变更评审清单
5. 有发布前演练与回滚要求

## 当前项目真正还缺的准备项

下面这些不是通用研发口号，而是结合当前 `PROJECT-主文档.md`、历史 Prisma 示例、现有业务边界后，正式开 schema 之前必须补齐的领域决策。

### 1. 租户边界还没冻结

当前文档同时存在两种口径：

- 一部分地方按 `org_id` 多租户共享库在描述
- 一部分 Prisma 示例又没有把 `org_id` 贯穿到 `Quote`、`Contract`、`Customer`、`RuleConfig` 等核心表

这会直接影响：

- 主键 / 唯一约束设计
- RLS 策略
- 查询索引
- 审计归属

正式建表前必须先定：

1. MVP 是否先按单租户实现
2. 如果不是单租户，哪些表必须带 `org_id`
3. 哪些表是全局表，哪些表是租户表
4. 飞书组织同步进来后，用户与部门是否天然绑定单一组织

### 2. Quote / Tender / Contract / Project 的关系还不够硬

主文档里这几个对象的关系很多，但还没有真正冻结成“唯一可执行关系图”。

现在至少有这些待定点：

- `Project` 到底是不是只读投影，还是会被真正建表
- `Quote -> Contract` 是单向生成关系，还是允许后补关联
- `Contract` 的来源字段是否允许同时挂 `source_quote_id` 和 `source_tender_id`
- `Tender` 是否进入 MVP，还是只保留预留字段

正式建表前必须先定：

1. 哪些对象在 MVP 真建表
2. 哪些对象先不落表，只保留视图或占位
3. 哪些关联必须强约束，哪些允许为空

### 3. 报价版本语义还没冻结

当前设计里既有：

- `quote_number`
- `version`
- `parent_uuid`
- `QuoteHistory`

但还没完全回答：

- 修改报价是更新原行，还是复制出新版本
- 已发送报价是否允许原地编辑
- 被拒绝后新版本是否沿用原 `quote_number`
- “作废”是状态流转、软删除，还是历史归档

这件事不定，后面审批、发送记录、合同生成、审计都会乱。

正式建表前必须先定：

1. 版本单位是“行版本”还是“快照版本”
2. 哪些状态下允许新建版本
3. 版本链如何追溯
4. 客户看到的对外编号如何稳定

### 4. 合同审核运行模型还没冻结

当前文档已经有 `Contract`、`ContractReview`、`ReviewIssue`，但仍缺几个关键决定：

- 一个合同允许多少次审核
- 审核重跑时是覆盖结果还是追加新 run
- 当前生效审核结果怎么判定
- 规则版本、模型版本、OCR版本是否都要落库
- Word 批注文件、HTML 报告、结构化问题列表的主从关系是什么

正式建表前必须先定：

1. `ContractReview` 是否就是“审核运行记录”
2. 是否需要 `latest_review_id` 或等价机制
3. OCR 结果与审核结果是否拆层存储
4. 错误重试是否保留历史失败 run

### 5. 文件资产模型还没冻结

当前文档已经明确原始文件走 MinIO，但数据库里还缺统一口径：

- 原始合同文件存什么
- OCR 中间产物存什么
- 批注文档存什么
- HTML 报告存什么
- 是否存 checksum / bucket / object_key / mime / size / uploader

如果继续只用 `original_file`、`annotated_file` 这种字符串字段，后面文件治理会很快失控。

正式建表前必须先定：

1. 是否引入统一 `file_objects` 表
2. 文件元数据与业务表如何关联
3. 是否记录哈希避免重复上传
4. 是否区分用户上传文件、系统生成文件、临时中间文件

### 6. 审批模型还没落表

业务里已经有折扣审批、法务审批、飞书审批通知，但现有示例 schema 里没有真正成型的审批表结构。

正式建表前必须先定：

1. 审批是通用引擎，还是 Quote / Contract 各自一套
2. 审批节点、审批人、审批意见、审批快照放在哪
3. 飞书审批是外部镜像，还是系统内主记录
4. 审批通过后如何回写业务状态

### 7. 客户主数据规则还没冻结

当前有 `Customer` / `Contact`，但还没定清：

- 客户唯一性按什么判断
- 同名客户如何处理
- 联系人是否允许跨客户复用
- 销售归属变更如何保留历史

正式建表前必须先定：

1. 客户去重策略
2. 联系人主联系人唯一规则
3. 客户状态流转与归档策略
4. 是否需要客户外部系统映射 ID

### 8. 组织与身份映射还没冻结

文档中有飞书组织同步、部门树、角色权限，但正式 schema 还缺这些决定：

- 用户主身份以本地用户为准，还是以飞书 open_id / union_id 为准
- 部门是否允许多归属
- 角色是系统级、组织级，还是用户在部门中的岗位级

正式建表前必须先定：

1. 身份主键策略
2. 飞书映射字段集合
3. 用户、部门、角色三者关系
4. 离职/禁用用户的保留策略

### 9. 规则配置与审核版本还没冻结

合同审核依赖规则配置，但当前还没定：

- `RuleConfig` 是整包版本，还是单条规则版本
- `ReviewIssue.rule_id` 对应的是规则定义还是规则实例
- 规则发布是否需要草稿、已发布、废弃三态

正式建表前必须先定：

1. 规则版本粒度
2. 审核结果如何精确追溯规则版本
3. 配置回滚是否只改“当前版本指针”
4. 规则是否区分租户级与系统级

### 10. 审计、事件、状态历史还没分层

当前文档非常强调审计，但数据库侧还没冻结这三类记录的分工：

- 审计日志
- 领域事件
- 状态变更历史

这三者不是一回事，不能混成一个表。

正式建表前必须先定：

1. 审计日志是否只记录“谁在何时改了什么”
2. 领域事件是否服务异步流程
3. 状态历史是否独立支撑页面时间线
4. 哪些行为必须三者都记，哪些只记其一

### 11. 软删除与归档策略还没冻结

现在文档里已经出现“作废”“归档”“历史版本”“配置回滚”，但缺统一约定：

- 哪些表允许软删除
- 哪些表只能作废，不能删
- 哪些表只归档不删除

正式建表前必须先定：

1. `Quote`、`Contract`、`Customer`、`RuleConfig` 各自删除策略
2. 审计与审核结果是否允许物理删除
3. 文件对象是否跟随业务记录级联清理

### 12. 敏感数据分级还没冻结

客户联系人、合同文本、审批意见、审核结论，敏感级别不一样。

正式建表前必须先定：

1. 哪些字段明文可存
2. 哪些字段需要字段级加密
3. 哪些字段只能对象存储，不进数据库
4. 哪些字段默认不进入全文检索

## 建表前必须冻结的领域决策

如果只允许补一轮准备项，我建议至少冻结下面这 12 个问题：

1. MVP 是否单租户，还是从第一天就共享库多租户
2. `Project` 是否真正建表
3. `Tender` 是否进入第一批 schema
4. 报价版本是原地更新还是新版本新行
5. 合同审核是否保留多次 run 历史
6. 文件是否引入统一文件对象表
7. 审批是否做成通用审批引擎
8. 客户去重规则是什么
9. 飞书身份映射字段是什么
10. 规则配置如何版本化
11. 审计 / 事件 / 状态历史怎么分层
12. 哪些对象允许软删除

这 12 个问题不冻结，后面的 migration 虽然能写，但很大概率第一轮就返工。

## 首批 schema 推荐边界

为了避免一次把文档里的所有对象都落地，我建议第一批正式 schema 只覆盖当前 P0/P1 真需要的对象。

### 第一批建议纳入

- `organizations`
- `departments`
- `users`
- `roles`
- `customers`
- `contacts`
- `projects`（骨架表）
- `tenders`（骨架表）
- `quotes`
- `quote_items`
- `contracts`
- `contract_reviews`
- `review_issues`
- `rule_configs`
- `file_objects`
- `approval_requests`
- `approval_steps`
- `audit_logs`

### 第一批建议暂缓

- `knowledge_items`
- `case_studies`
- `schedules`
- 通用 Agent 记忆相关表

原因很简单：这些对象虽然在总文档里存在，但当前活动业务仓并没有对应实现落点，先全建出来只会制造空表和迁移噪音。

### 骨架表定义原则

这里的 `projects` / `tenders` “进入第一批”，指的是先建立长期主干，不是一次性把周边复杂字段全铺满。

骨架表最低要求：

- 主键与稳定业务编号
- 所属组织 / 负责人
- 来源关联字段
- 生命周期状态
- 创建 / 更新时间

第一批不强求：

- 全量页面字段
- 全量统计字段
- 复杂衍生字段
- 所有外围联动表

这条做法既符合工程通识，也符合你说的“框架一步到位”的方向，但前提是先落主干，不落空壳。

## 第一批 schema 的最低补充约束

对当前项目，除通用规则外，我建议额外强制以下约束：

1. 所有核心业务表必须先决定是否带 `org_id`
2. 所有列表页主查询都要设计成 `org_id + status + created_at` 或等价索引
3. `quotes` 必须明确版本链约束
4. `contract_reviews` 必须能追溯规则版本、模型版本、文件版本
5. `file_objects` 必须有 `storage_provider + bucket + object_key + checksum`
6. 审计日志必须记录 actor、target、diff、request_id
7. 客户与联系人必须明确唯一性和主联系人规则
8. 规则配置必须支持启用、停用、回滚

## 单一真相原则

后端正式启动后，数据库结构必须只有一个可执行真相入口。

默认建议：

- 若沿用当前文档口径，优先采用 `prisma/schema.prisma + prisma/migrations/`
- 若改用其他工具，例如 Drizzle 或纯 SQL migration，也可以，但必须在本文件中显式改写真相入口

禁止状态：

- 主文档写一套
- 代码里再写一套
- SQL 手工改一套
- 最终没人说得清哪一份才算生效

## 表结构命名原则

### 表与列

- 表名使用复数 `snake_case`，例如 `contracts`、`quote_items`
- 列名使用 `snake_case`
- 主键统一为 `id`
- 外键统一为 `<entity>_id`，例如 `quote_id`、`created_by`

### 时间字段

除明确豁免外，业务主表至少应有：

- `created_at`
- `updated_at`

按需要增加：

- `deleted_at`：仅在真的采用软删除时加入
- `created_by`
- `updated_by`

### 状态字段

状态字段不能是无约束自由文本。必须明确采用以下之一：

- 数据库枚举
- `CHECK` 约束
- 代码枚举 + 数据库约束同时存在

## 数据语义原则

### 金额

- 金额字段禁止使用浮点数
- 统一使用 `numeric(p, s)` 或“最小货币单位整数”
- 一个领域内只能选一种主策略，不能混用

### JSON

- `jsonb` 只能用于确实不稳定、难以规范化的扩展数据
- 核心查询字段、过滤字段、关联字段不得偷懒塞进 `jsonb`

### 删除策略

- 默认优先硬删除 + 审计日志，或显式软删除
- 一张表只能有一套删除语义
- 不能同一领域一部分接口当硬删，一部分接口当软删

## 多租户与权限原则

每张业务表都必须声明租户边界：

- `org_id` / `tenant_id` 强约束
- 或者明确说明它是全局表

若表位于 Supabase 可被用户侧访问的 schema 中，默认要求：

- 明确 RLS 策略
- 明确 service role 绕过点
- 明确谁可读、谁可写、谁可删

没有租户策略或权限矩阵的表，不允许进入正式环境。

## 索引与约束原则

- 每个外键都要有索引，除非能说明查询路径永远不走它
- 每个业务唯一键都要落成数据库唯一约束，不能只靠代码判断
- 复合索引必须对应真实查询路径，不允许凭感觉堆索引
- 冗余索引要定期清理

最低检查项：

1. 主查询条件有没有索引
2. 排序字段和过滤字段的组合是否合理
3. 唯一约束是否覆盖业务主键语义
4. 外键级联策略是否明确

## 迁移治理原则

### 基本规则

- 禁止直接在生产库手工改结构后再回填到代码
- 所有结构变更必须通过版本化 migration 进入仓库
- migration 必须可重复审查，可在 staging 演练

### 零停机规则

生产变更默认遵循 `expand -> migrate -> contract`：

1. 先加新列 / 新表 / 新索引
2. 再双写或回填
3. 再切换读路径
4. 最后删除旧结构

禁止把以下操作一次性塞进同一发布窗口：

- 新列上线
- 历史数据全量回填
- 旧列删除
- 读取逻辑切换

### 回填规则

- 回填脚本必须幂等
- 大批量更新必须分批执行
- 要能中断后继续
- 需要记录影响范围和耗时

### 风险操作

以下操作默认需要额外评审：

- 删表
- 删列
- 列重命名
- 类型缩窄
- 大表新增非空列
- 修改唯一约束
- 调整 RLS 策略

## 评审检查清单

每次表结构 PR 至少回答以下问题：

1. 这次变更的业务对象是什么
2. 真正的租户边界是什么
3. 为什么需要这张表 / 这个字段
4. 生命周期如何结束
5. 查询路径是什么，索引是否匹配
6. 是否涉及历史数据回填
7. 是否影响旧版本代码兼容
8. 是否需要 RLS / 审计 / 归档

## 动态治理落地要求

当后端正式开工时，至少补齐以下资产：

### Stage 1：建立真相入口

- 在 `product-truth/product-code` 内创建真实 schema 目录
- 创建版本化 migration 目录
- 明确使用 Prisma、Drizzle 或纯 SQL 之一

### Stage 2：接入 CI

若采用 Prisma，最低要求：

```bash
pnpm prisma format
pnpm prisma validate
pnpm prisma migrate status
```

若采用其他方案，也必须提供等价校验命令。

### Stage 3：接入发布门禁

- schema 变更 PR 必须附 migration
- 生产前必须做 staging 演练
- 高风险 migration 必须附回滚说明
- RLS 变更必须附权限验证结果

## 当前非真相来源

以下内容目前都不能视为正式生效的数据库真相：

- `PROJECT-主文档.md` 里的 Prisma / SQL 示例
- `guide-开发环境准备.md` 附录中的示例 SQL
- 根目录 `setup.sh` 内置的初始化 SQL

它们可以作为设计参考，但不能替代真实 schema 与 migration 目录。

## 当前建议

如果你接下来要认真做后端，这条线建议直接这么收口：

1. 在 `product-truth/product-code` 里选定唯一 schema 工具
2. 建立 migration 目录
3. 用 CI 把校验跑起来
4. 让本文件只管规则，不再承载伪实现

在当前仓库语境下，如果没有特殊理由，延续 Prisma 会比重新换一套口径更省认知成本，因为现有主文档和历史设计大多已经按 Prisma 在说话。
