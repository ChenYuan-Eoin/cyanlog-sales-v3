**Status**: confirmed

## 1. 单元定义

**目标**：在配置中心维护组织基础面和访问控制面，让 `F003` 的鉴权执行、`F004` 的审批执行、`F002` 的报价数据范围都有稳定配置来源。

`F011` 必须分成两个子面理解，而不是做成一个“角色勾权限”的页面：

### 1.1 组织架构管理
- 部门树
- 成员档案
- 主部门 / 兼职部门
- 部门数据范围
- 外部通讯录同步入口（如飞书）

### 1.2 角色权限管理
- 角色定义
- 角色拥有的业务能力
- 角色的数据范围 / 作用域
- 成员与角色分配
- 审批代理 / 转交范围等组织策略

**这包不拥有的内容**：
- 登录、发 token、会话校验
- 中间件鉴权执行
- 报价或合同的具体审批动作
- 合同审核规则内容

这些分别属于 `F003 / F004 / F009`。

## 3. 配置对象

### 3.1 组织架构管理对象
- 部门层级
- 人员归属
- 上下级关系
- 部门归属和可见范围
- 外部源同步状态

### 3.2 角色权限管理对象
- 系统预置角色
- 自定义角色
- 角色与业务能力关系
- 角色分配成员
- 角色分配作用域

### 3.3 数据范围
- `OWN`：仅本人
- `DEPT`：本部门及下级部门
- `SPACE`：历史绑定标识。现行部门授权使用 `DEPT`。
- `ORG`：全组织

### 3.4 审批组织策略
- 代理人设置
- 转交范围
- 升级链可见范围

### 3.5 部门与数据范围

- 每个启用部门就是一个可选数据范围，选项使用组织架构中的部门 ID。平台超管可在当前有效组织选择获授权的部门。新部门随组织树进入选项，名称、层级和可见性在改名、改隶、停用和重新授权后重新计算。
- Team Leader 的授权范围是所负责各部门及下级的并集。工作台提供「授权范围汇总」「仅本部门」「含下级部门」三种视图，并按当前授权取交集。华南负责人可以选授权内的大部门和小部门，公司同层的未授权平台部不显示，也不能直接查询。重叠部门和成员分别去重。
- 既有业务记录通过原关联键追溯所属部门。历史记录关联用于兼容读取，现行选择和授权均来自当前部门树。既有空间绑定继续可核对和撤销。
- 查看部门成员使用已生效的权威目录，包含同步在职但尚未登录的员工。部门树统计含下级，部门名单按当前所选范围取数。目录不可核对时显示未核实状态，历史成员和本地成员通过对应筛选查看。

### 3.6 角色人数、保存和超管任命

- 角色列表和详情通过角色 ID 与有效作用域核对同一份数据。已生效成员、待生效成员、有效绑定分别统计；一名成员的多个有效绑定只计一名。待生效成员以服务端确认的首次登录预分配为准。
- 保存角色权限时校验当前组织、角色和原授权快照，并回读保存结果。超级管理员任免在目录中登记为一个受保护动作。在组织绑定批次中，两个入口统一到唯一的「超级管理员」角色，并保留指定系统账号的保护规则。

### 3.7 当前权限整改的业务验收

按 `IN-20261126-001`，先验收「系统菜单 → 功能区 → 可授权动作」。目录项逐个对应实际页面、按钮及后端校验。菜单可见性随可访问功能变化。旧后台入口与通配授予退出可勾选目录，待接入动作标记为不可勾选。

本批验证组织与权限及自助收寄。业务角色分配、资料编辑、角色定义保存、超管任免分别校验。寄件台账、工单处理、确认下单、承运商操作和设置分别校验。侧栏「寄件设置」与配置中心「寄件配置」共用同一套权限。目标回归须重放授权、实际操作、撤销及服务端拒绝。目录动作验收后再验证角色、组织和部门的数据范围绑定。

日期栏三按钮保持独立候选及生产验收。其他业务模块的功能整改保留在各自的本地工作中。

| 功能 | 拥有者 |

否则很容易把“合同规则”“组织架构”“权限校验逻辑”“审批流动作”混成一个模块，最后任何一处改动都会牵动整条链。

## 5. 数据建模原则

推荐强类型对象：
- `organizations`
- `departments`
- `users`
- `user_departments`
- `roles`
- `user_roles`
- `sales_spaces`
- `delegation_rules`

MVP 可以复用已有角色表，但必须保证：
- 组织配置可管理
- 菜单权限不是写死在前端
- 数据范围可被后端执行
- 作用域至少覆盖 `org / department / space`

这里有一个关键判断：

**后端权限键可以继续存在，但它只是执行码，不是产品模型本身。**

前台角色权限页必须按以下三层呈现：
1. 能访问哪些管理域 / 业务域
2. 能执行哪些业务动作
3. 数据范围落在哪些组织作用域

角色权限页可以使用三栏，但三栏必须形成权限闭环：

| 栏位 | 内容 | 验收标准 |
|------|------|----------|
| 左栏：角色列表 | 角色、成员数、作用域数、发布/保存状态 | 一眼看到角色资产和异常角色 |
| 中栏：权限矩阵 | 按业务域分组的权限点、动作、数据范围和继承来源 | 权限编辑密度高，避免把每个权限做成大卡片；可批量切换和搜索 |
| 右栏：闭环摘要 | 当前角色能访问什么、影响哪些成员和部门、是否可发布、需要刷新哪些上下文 | 能回答“这个角色实际会造成什么效果，以及下一步做什么” |

权限点展示必须优先使用矩阵、表格或紧凑列表。只有复杂策略说明、冲突说明、发布阻断和影响范围适合放到右栏卡片。不得把大量 checkbox 逐个做成宽松卡片，导致用户无法快速判断权限链条。

## 6. 客户端能力要求

### 6.1 配置中心前端

应拆成两个入口，不可混进合同规则：

#### A. 组织架构
- 组织树浏览
- 成员列表
- 部门层级和成员关系展示
- 外部通讯录同步入口
- 跳转真实组织后台

#### A.1 外部通讯录同步 MVP（飞书）

当前阶段承诺“飞书部门树、成员基础档案和主部门关系同步”。手机号、岗位、头像等字段在飞书返回且系统字段可承载时写入。汇报关系和角色分配单独维护，工作台直接使用当前部门树。

同步入口必须具备明确反馈，而不是只提供一个按钮：
- 未配置 `FEISHU_APP_ID` / `FEISHU_APP_SECRET` 时，前端必须展示“飞书同步未配置”、缺失项和下一步配置位置（Vercel 环境变量 / 本地 `.env.local`）。
- 同步成功时，前端必须展示部门新增/更新/失败/总数，以及成员新增/更新/跳过/失败/总数，并刷新组织架构摘要。
- 只拿到 root、0 个可访问部门、部门或成员局部失败时，必须显示“部分完成/失败原因”，不能展示为完整同步成功。
- 上游飞书接口失败时，接口必须返回可识别错误码和排障提示，前端必须展示失败原因。
- 文案必须明确“当前 MVP 同步部门、成员和主部门关系，不自动完成角色分配和完整通讯录治理”，避免把外部组织同步误解为权限体系已自动配置完成。

#### B. 角色权限
- 角色列表
- 业务能力分组展示
- 数据范围说明
- 角色绑定成员
- 角色绑定作用域
- 代理策略配置

### 6.2 业务前端
- 导航按权限展示
- 无权限时明确拒绝
- 列表按数据范围过滤
- 审批链按组织作用域命中

## 7. 当前实现判断

当前工程不是“完全没有组织权限能力”，而是**已有组织后台与作用域数据模型，但配置中心又额外做了一套简化版角色面板**。

已经存在的真实能力：
- `/api/admin/org`
- `/admin/org`
- `departments / user_departments / user_roles / sales_spaces`
- `scope_type = org / department / space`

当前错误点：
- 把“组织与权限”错误放进“治理与规则”
- 把权限模型做成一组裸露的后端动作码 checkbox
- 没有把已有 `admin/org` 的真实能力收回到配置中心信息架构

因此下一轮重点不是再造一套组织系统，而是：
1. 把信息架构改正
2. 把配置中心收口到真实组织后台能力
3. 用业务能力分组重表达角色权限

## 10. 人员列表行内操作设计

### 10.1 操作优先级分类

| 优先级 | 操作 | 场景 | 交互方式 |
|--------|------|------|----------|
| **P0** | 编辑 | 修改姓名、邮箱、职位、手机 | 行内点击 → Dialog |
| **P0** | 分配角色 | 赋予/撤销角色权限 | Dialog 内角色多选 |
| **P0** | 重置密码 | 管理员帮用户重置密码 | AlertDialog 确认 → 显示临时密码 |
| **P0** | 停用/启用 | 离职/休假处理（布尔状态） | Switch 切换 + AlertDialog 确认 |
| **P1** | 允许/禁止登录 | 临时封禁（独立于停用） | Switch 切换 |
| **P1** | 修改汇报对象 | 调整组织架构汇报线 | Dialog 内人员选择器 |
| **P1** | 重设主属部门 | 转岗 | Dialog 内部门树选择 |
| **P1** | 激活 | 首次激活/重新激活 | 系统逻辑自动，无需单独操作 |
| **P2** | 重设附属部门 | 清除兼职部门 | Dialog 内多选部门 |
| **P2** | 追加/删除附属部门 | 添加/移除兼职部门 | 行内 Badge + Dialog 管理 |
| **P2** | 激活拇醒 | 催促激活邮件 | 按钮 → 发送成功 Toast |

### 10.2 行内操作布局（参考纷享销客）

**主区域**（直接显示，最多3个）：
```
[编辑] [角色] [更多...]
```

**"更多"下拉菜单（shadcn DropdownMenu）**：
- 重置密码
- 状态: [启用/停用]（Switch）
- 登录: [允许/禁止]（Switch）
- 部门管理 → 打开部门 Dialog
- 汇报对象 → 打开人员选择 Dialog
- 激活拇醒（如未激活）

### 10.3 组件选型（shadcn/ui）

| 组件 | 用途 | 位置 |
|------|------|------|
| `Dialog` | 编辑表单、角色分配、部门选择 | 行内点击触发 |
| `AlertDialog` | 停用/删除确认、密码重置确认 | 需要确认的操作前 |
| `Switch` | 启用/停用、允许/禁止登录 | Dialog 内或行内 |
| `Select` / `Popover` | 部门树选择、汇报对象选择 | Dialog 内 |
| `DropdownMenu` | "更多"收纳次要操作 | 行内"更多"按钮 |
| `Badge` | 显示当前状态（在职/已停用/未激活） | 行内姓名旁 |
| `Tooltip` | 操作按钮提示说明 | 图标按钮上 |

### 10.4 状态流转图

```
在职 ──[停用]──> 已停用 ──[启用]──> 在职
 │                                  │
[删除]                            [编辑]
 ▼                                  ▼
软删除（保留数据）              更新信息
```

### 10.5 API 接口需求

| 操作 | 方法 | 接口 | 说明 |
|------|------|------|------|
| 编辑 | PATCH | `/api/admin/users/{id}` | 更新基本信息 |
| 分配角色 | POST | `/api/admin/users/{id}/roles` | 批量替换角色 |
| 重置密码 | POST | `/api/admin/users/{id}/reset-password` | 生成临时密码 |
| 停用/启用 | PATCH | `/api/admin/users/{id}/status` | status: active/inactive |
| 允许/禁止登录 | PATCH | `/api/admin/users/{id}/login-enabled` | login_enabled: boolean |
| 修改汇报对象 | PATCH | `/api/admin/users/{id}/report-to` | report_to_user_id |
| 重设主属部门 | PATCH | `/api/admin/users/{id}/primary-dept` | primary_dept_id |
| 管理附属部门 | POST/DELETE | `/api/admin/users/{id}/departments` | 兼职部门增删 |
| 激活拇醒 | POST | `/api/admin/users/{id}/resend-activation` | 发送激活邮件 |
| 删除 | DELETE | `/api/admin/users/{id}` | 软删除 |

### 10.6 验收标准

- [ ] 人员列表每行显示操作按钮（编辑/角色/更多）
- [ ] DropdownMenu 不被表格遮挡（已验证 Portal 方案）
- [ ] 所有 P0 功能可用
- [ ] 状态变更需二次确认
- [ ] 敏感操作（删除/停用）记录审计日志
