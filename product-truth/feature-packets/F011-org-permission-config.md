# Feature Packet: F011-组织权限配置

**Created**: 2026-06-09

**Status**: confirmed  
**Parent**: 配置中心  
**Depends On**: `F000-config-center-architecture`

---

## 1. 单元定义

**目标**：在配置中心维护组织基础面和访问控制面，让 `F003` 的鉴权执行、`F004` 的审批执行、`F002` 的报价数据范围都有稳定配置来源。

`F011` 必须分成两个子面理解，而不是做成一个“角色勾权限”的页面：

### 1.1 组织架构管理
- 部门树
- 成员档案
- 主部门 / 兼职部门
- 销售空间
- 外部通讯录同步入口（如飞书）

### 1.2 角色权限管理
- 角色定义
- 角色拥有的业务能力
- 角色的数据范围 / 作用域
- 成员与角色分配
- 审批代理 / 转交范围等组织策略

**这包不拥有的内容**：
- 登录、发 token、会话校验
- 中间件鉴权执行
- 报价或合同的具体审批动作
- 合同审核规则内容

这些分别属于 `F003 / F004 / F009`。

## 2. 三层落位

| 层级 | 本功能对应物 |
|------|--------------|
| 第一层：能力域 | 组织权限配置 |
| 第二层：具体配置 | 部门树、角色、权限点、数据范围、代理策略 |
| 第三层：消费页面 | 登录后导航、角色管理、待办审批、业务列表权限过滤 |

## 3. 配置对象

### 3.1 组织架构管理对象
- 部门层级
- 人员归属
- 上下级关系
- 销售空间归属
- 外部源同步状态

### 3.2 角色权限管理对象
- 系统预置角色
- 自定义角色
- 角色与业务能力关系
- 角色分配成员
- 角色分配作用域

### 3.3 数据范围
- `OWN`：仅本人
- `DEPT`：本部门及下级部门
- `SPACE`：指定销售空间
- `ORG`：全组织

### 3.4 审批组织策略
- 代理人设置
- 转交范围
- 升级链可见范围

## 4. 与 F003 / F004 / F009 的边界

| 功能 | 拥有者 |
|------|--------|
| 用户登录 / token 签发 / session | `F003` |
| 权限中间件执行 | `F003` |
| 审批动作执行 | `F004` |
| 合同审核规则内容 | `F009` |
| 组织、角色、数据范围配置 | `F011` |

这条边界非常关键。

否则很容易把“合同规则”“组织架构”“权限校验逻辑”“审批流动作”混成一个模块，最后任何一处改动都会牵动整条链。

## 5. 数据建模原则

推荐强类型对象：
- `organizations`
- `departments`
- `users`
- `user_departments`
- `roles`
- `user_roles`
- `sales_spaces`
- `delegation_rules`

MVP 可以复用已有角色表，但必须保证：
- 组织配置可管理
- 菜单权限不是写死在前端
- 数据范围可被后端执行
- 作用域至少覆盖 `org / department / space`

这里有一个关键判断：

**后端权限键可以继续存在，但它只是执行码，不是产品模型本身。**

前台角色权限页必须按以下三层呈现：
1. 能访问哪些管理域 / 业务域
2. 能执行哪些业务动作
3. 数据范围落在哪些组织作用域

## 6. 客户端能力要求

### 6.1 配置中心前端

应拆成两个入口，不可混进合同规则：

#### A. 组织架构
- 组织树浏览
- 成员列表
- 部门/成员/销售空间关系展示
- 外部通讯录同步入口
- 跳转真实组织后台

#### A.1 外部通讯录同步 MVP（飞书）

当前阶段承诺“飞书部门树、成员基础档案和主部门关系同步”。手机号、岗位、头像等字段在飞书返回且系统字段可承载时写入；汇报关系、角色分配、销售空间精细映射不在第一阶段自动完成。

同步入口必须具备明确反馈，而不是只提供一个按钮：
- 未配置 `FEISHU_APP_ID` / `FEISHU_APP_SECRET` 时，前端必须展示“飞书同步未配置”、缺失项和下一步配置位置（Vercel 环境变量 / 本地 `.env.local`）。
- 同步成功时，前端必须展示部门新增/更新/失败/总数，以及成员新增/更新/跳过/失败/总数，并刷新组织架构摘要。
- 只拿到 root、0 个可访问部门、部门或成员局部失败时，必须显示“部分完成/失败原因”，不能展示为完整同步成功。
- 上游飞书接口失败时，接口必须返回可识别错误码和排障提示，前端必须展示失败原因。
- 文案必须明确“当前 MVP 同步部门、成员和主部门关系，不自动完成角色分配和完整通讯录治理”，避免把外部组织同步误解为权限体系已自动配置完成。

#### B. 角色权限
- 角色列表
- 业务能力分组展示
- 数据范围说明
- 角色绑定成员
- 角色绑定作用域
- 代理策略配置

### 6.2 业务前端
- 导航按权限展示
- 无权限时明确拒绝
- 列表按数据范围过滤
- 审批链按组织作用域命中

## 7. 当前实现判断

当前工程不是“完全没有组织权限能力”，而是**已有组织后台与作用域数据模型，但配置中心又额外做了一套简化版角色面板**。

已经存在的真实能力：
- `/api/admin/org`
- `/admin/org`
- `departments / user_departments / user_roles / sales_spaces`
- `scope_type = org / department / space`

当前错误点：
- 把“组织与权限”错误放进“治理与规则”
- 把权限模型做成一组裸露的后端动作码 checkbox
- 没有把已有 `admin/org` 的真实能力收回到配置中心信息架构

因此下一轮重点不是再造一套组织系统，而是：
1. 把信息架构改正
2. 把配置中心收口到真实组织后台能力
3. 用业务能力分组重表达角色权限

## 10. 人员列表行内操作设计

### 10.1 操作优先级分类

| 优先级 | 操作 | 场景 | 交互方式 |
|--------|------|------|----------|
| **P0** | 编辑 | 修改姓名、邮箱、职位、手机 | 行内点击 → Dialog |
| **P0** | 分配角色 | 赋予/撤销角色权限 | Dialog 内角色多选 |
| **P0** | 重置密码 | 管理员帮用户重置密码 | AlertDialog 确认 → 显示临时密码 |
| **P0** | 停用/启用 | 离职/休假处理（布尔状态） | Switch 切换 + AlertDialog 确认 |
| **P1** | 允许/禁止登录 | 临时封禁（独立于停用） | Switch 切换 |
| **P1** | 修改汇报对象 | 调整组织架构汇报线 | Dialog 内人员选择器 |
| **P1** | 重设主属部门 | 转岗 | Dialog 内部门树选择 |
| **P1** | 激活 | 首次激活/重新激活 | 系统逻辑自动，无需单独操作 |
| **P2** | 重设附属部门 | 清除兼职部门 | Dialog 内多选部门 |
| **P2** | 追加/删除附属部门 | 添加/移除兼职部门 | 行内 Badge + Dialog 管理 |
| **P2** | 激活拇醒 | 催促激活邮件 | 按钮 → 发送成功 Toast |

### 10.2 行内操作布局（参考纷享销客）

**主区域**（直接显示，最多3个）：
```
[编辑] [角色] [更多...]
```

**"更多"下拉菜单（shadcn DropdownMenu）**：
- 重置密码
- 状态: [启用/停用]（Switch）
- 登录: [允许/禁止]（Switch）
- 部门管理 → 打开部门 Dialog
- 汇报对象 → 打开人员选择 Dialog
- 激活拇醒（如未激活）

### 10.3 组件选型（shadcn/ui）

| 组件 | 用途 | 位置 |
|------|------|------|
| `Dialog` | 编辑表单、角色分配、部门选择 | 行内点击触发 |
| `AlertDialog` | 停用/删除确认、密码重置确认 | 需要确认的操作前 |
| `Switch` | 启用/停用、允许/禁止登录 | Dialog 内或行内 |
| `Select` / `Popover` | 部门树选择、汇报对象选择 | Dialog 内 |
| `DropdownMenu` | "更多"收纳次要操作 | 行内"更多"按钮 |
| `Badge` | 显示当前状态（在职/已停用/未激活） | 行内姓名旁 |
| `Tooltip` | 操作按钮提示说明 | 图标按钮上 |

### 10.4 状态流转图

```
在职 ──[停用]──> 已停用 ──[启用]──> 在职
 │                                  │
[删除]                            [编辑]
 ▼                                  ▼
软删除（保留数据）              更新信息
```

### 10.5 API 接口需求

| 操作 | 方法 | 接口 | 说明 |
|------|------|------|------|
| 编辑 | PATCH | `/api/admin/users/{id}` | 更新基本信息 |
| 分配角色 | POST | `/api/admin/users/{id}/roles` | 批量替换角色 |
| 重置密码 | POST | `/api/admin/users/{id}/reset-password` | 生成临时密码 |
| 停用/启用 | PATCH | `/api/admin/users/{id}/status` | status: active/inactive |
| 允许/禁止登录 | PATCH | `/api/admin/users/{id}/login-enabled` | login_enabled: boolean |
| 修改汇报对象 | PATCH | `/api/admin/users/{id}/report-to` | report_to_user_id |
| 重设主属部门 | PATCH | `/api/admin/users/{id}/primary-dept` | primary_dept_id |
| 管理附属部门 | POST/DELETE | `/api/admin/users/{id}/departments` | 兼职部门增删 |
| 激活拇醒 | POST | `/api/admin/users/{id}/resend-activation` | 发送激活邮件 |
| 删除 | DELETE | `/api/admin/users/{id}` | 软删除 |

### 10.6 验收标准

- [ ] 人员列表每行显示操作按钮（编辑/角色/更多）
- [ ] DropdownMenu 不被表格遮挡（已验证 Portal 方案）
- [ ] 所有 P0 功能可用
- [ ] 状态变更需二次确认
- [ ] 敏感操作（删除/停用）记录审计日志
