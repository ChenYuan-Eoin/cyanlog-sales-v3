# Feature Packet: F011-组织权限配置

**Created**: 2026-06-09  
**REQ ID**: F011  
**Status**: confirmed  
**Parent**: 配置中心  
**Depends On**: `F000-config-center-architecture`

---

## 1. 单元定义

**目标**：在配置中心维护组织基础面和访问控制面，让 `F003` 的鉴权执行、`F004` 的审批执行、`F002` 的报价数据范围都有稳定配置来源。

`F011` 必须分成两个子面理解，而不是做成一个“角色勾权限”的页面：

### 1.1 组织架构管理
- 部门树
- 成员档案
- 主部门 / 兼职部门
- 销售空间
- 外部通讯录同步入口（如飞书）

### 1.2 角色权限管理
- 角色定义
- 角色拥有的业务能力
- 角色的数据范围 / 作用域
- 成员与角色分配
- 审批代理 / 转交范围等组织策略

**这包不拥有的内容**：
- 登录、发 token、会话校验
- 中间件鉴权执行
- 报价或合同的具体审批动作
- 合同审核规则内容

这些分别属于 `F003 / F004 / F009`。

## 2. 三层落位

| 层级 | 本功能对应物 |
|------|--------------|
| 第一层：能力域 | 组织权限配置 |
| 第二层：具体配置 | 部门树、角色、权限点、数据范围、代理策略 |
| 第三层：消费页面 | 登录后导航、角色管理、待办审批、业务列表权限过滤 |

## 3. 配置对象

### 3.1 组织架构管理对象
- 部门层级
- 人员归属
- 上下级关系
- 销售空间归属
- 外部源同步状态

### 3.2 角色权限管理对象
- 系统预置角色
- 自定义角色
- 角色与业务能力关系
- 角色分配成员
- 角色分配作用域

### 3.3 数据范围
- `OWN`：仅本人
- `DEPT`：本部门及下级部门
- `SPACE`：指定销售空间
- `ORG`：全组织

### 3.4 审批组织策略
- 代理人设置
- 转交范围
- 升级链可见范围

---

## 4. 与 F003 / F004 / F009 的边界

| 功能 | 拥有者 |
|------|--------|
| 用户登录 / token 签发 / session | `F003` |
| 权限中间件执行 | `F003` |
| 审批动作执行 | `F004` |
| 合同审核规则内容 | `F009` |
| 组织、角色、数据范围配置 | `F011` |

这条边界非常关键。

否则很容易把“合同规则”“组织架构”“权限校验逻辑”“审批流动作”混成一个模块，最后任何一处改动都会牵动整条链。

---

## 5. 数据建模原则

推荐强类型对象：
- `organizations`
- `departments`
- `users`
- `user_departments`
- `roles`
- `user_roles`
- `sales_spaces`
- `delegation_rules`

MVP 可以复用已有角色表，但必须保证：
- 组织配置可管理
- 菜单权限不是写死在前端
- 数据范围可被后端执行
- 作用域至少覆盖 `org / department / space`

这里有一个关键判断：

**后端权限键可以继续存在，但它只是执行码，不是产品模型本身。**

前台角色权限页必须按以下三层呈现：
1. 能访问哪些管理域 / 业务域
2. 能执行哪些业务动作
3. 数据范围落在哪些组织作用域

---

## 6. 客户端能力要求

### 6.1 配置中心前端

应拆成两个入口，不可混进合同规则：

#### A. 组织架构
- 组织树浏览
- 成员列表
- 部门/成员/销售空间关系展示
- 外部通讯录同步入口
- 跳转真实组织后台

#### B. 角色权限
- 角色列表
- 业务能力分组展示
- 数据范围说明
- 角色绑定成员
- 角色绑定作用域
- 代理策略配置

### 6.2 业务前端
- 导航按权限展示
- 无权限时明确拒绝
- 列表按数据范围过滤
- 审批链按组织作用域命中

---

## 7. 当前实现判断

当前工程不是“完全没有组织权限能力”，而是**已有组织后台与作用域数据模型，但配置中心又额外做了一套简化版角色面板**。

已经存在的真实能力：
- `/api/admin/org`
- `/admin/org`
- `departments / user_departments / user_roles / sales_spaces`
- `scope_type = org / department / space`

当前错误点：
- 把“组织与权限”错误放进“治理与规则”
- 把权限模型做成一组裸露的后端动作码 checkbox
- 没有把已有 `admin/org` 的真实能力收回到配置中心信息架构

因此下一轮重点不是再造一套组织系统，而是：
1. 把信息架构改正
2. 把配置中心收口到真实组织后台能力
3. 用业务能力分组重表达角色权限
