# Feature Packet: F026-考核编排与评分归档

**Created**: 2026-06-10  
**REQ ID**: F026  
**Status**: confirmed  
**Parent**: `F023-销售赋能与考核中心`  
**Depends On**: `F025`, `F018`, `F019`, `F003`

---

## 1. 单元定义

**目标**：把模拟考、正式考、补考、评分表、结果归档和收口协同收成一个执行面，并与现有日程引擎、账号状态底座协作，而不是重做一套通用提醒或账号系统。

`F026` 不是“一个带提醒的考试日历”，也不是“在题库后面多一个分数表”。

它要回答的是：
1. 某个岗位或某批成员在什么时间窗参加什么类型的考核
2. 这些考核如何从已发布蓝图生成具体计划、场次和参与人
3. 客观题、情景题、演练题分别如何记分、复核和确认结果
4. 未通过、缺考、补考、补学如何进入后续处理
5. 成员状态发生变化时，历史结果和未完成事项如何收口协同

这里有三个必须先锁死的判断：

**考核蓝图 != 考核计划**

- `F025` 的蓝图回答“应该按什么结构出题和评分”
- `F026` 的计划回答“这次谁来考、何时考、在哪考、怎么记结果”

**考核计划 != 通用日程项**

- `F026` 定义计划、场次、评分和结果
- `F018/F019` 只承接被派生出来的日程项与提醒规则

**认证结果 != 账号状态**

- `F026` 记录考核结果、认证状态、待处理事项
- `F003` 决定用户是否禁用、权限是否回收、会话是否失效

**这包拥有的内容**：
- 模拟考 / 正式考 / 补考计划
- 场次编排与参与人管理
- 日程反推规则
- 评分表、打分记录、复核规则
- 结果归档与认证状态
- 未通过项补学 / 补考 / 收口协同

**这包不拥有的内容**：
- 通用日程 CRUD、提醒通道发送
- 用户禁用、权限回收执行
- 岗位模型、题库对象、组卷蓝图定义
- 引导阶段任务和试用期阶段复核（属于 `F024`）

## 3. 用户与使用场景

### 3.1 考核运营
- 选择蓝图并生成计划
- 配置时间窗、场次、参与人、监考人
- 推送到 `F018/F019` 形成日程与提醒

### 3.2 评分人 / 经理 / 导师
- 查看待评分场次
- 按评分表打分
- 提交复核意见
- 确认通过 / 不通过 / 待补考

### 3.3 参考成员
- 查看考核安排
- 查看本人结果、补考安排、待补学项
- 获取认证状态或未通过原因

### 3.4 运营管理员
- 查看岗位维度或批次维度的通过率
- 归档历史记录
- 在成员状态变化前检查是否存在未完成考核或待处理项

## 4. 核心对象

### 4.1 考核计划

- `assessment_plans`
- `assessment_plan_participants`
- `assessment_plan_rules`

说明：
- 计划是一次运营层编排，不是题库蓝图
- 一个计划可以对应一个批次，也可以只对应单人补考
- 计划在创建时应绑定 `F025` 的蓝图版本快照

推荐字段：
- `plan_code`
- `plan_name`
- `assessment_scene`
- `blueprint_version_id`
- `target_scope_type`
- `window_start_at`
- `window_end_at`
- `status`

### 4.2 场次与日程联动

- `assessment_sessions`
- `assessment_attempts`
- `assessment_agenda_links`
- `assessment_proctor_assignments`

说明：
- 一个计划可以拆出多个场次
- 场次与 `F018` 的日程项通过 link 关联，而不是把日程字段完全内嵌进计划表
- `attempt` 是成员级执行对象，用来承接缺考、豁免、补考等状态

推荐字段：
- `session_code`
- `session_mode`
- `scheduled_start_at`
- `scheduled_end_at`
- `venue`
- `agenda_id`
- `proctor_user_id`

### 4.3 评分表与评分记录

- `score_sheet_templates`
- `score_sheets`
- `score_sheet_items`
- `score_entries`
- `scorer_assignments`

说明：
- 评分表模板是标准结构
- 评分表实例是针对某次场次 / 某个成员生成的执行对象
- 客观题分数可自动写入，情景题 / 演练题 / 口述题保留人工评分入口

推荐字段：
- `template_code`
- `sheet_code`
- `attempt_id`
- `scoring_mode`
- `max_score`
- `actual_score`
- `review_status`

### 4.4 结果与认证记录

- `assessment_results`
- `certification_records`
- `remedial_actions`
- `resit_recommendations`

说明：
- 结果对象承接某次考核的最终结论
- 认证记录承接持续状态，不与单次结果强绑定为同一张表
- 未通过不一定直接补考，也可能先补学再复测

推荐字段：
- `result_status`
- `pass_line`
- `final_score`
- `decision_reason`
- `certification_status`
- `valid_until`

### 4.5 收口协同

- `closure_actions`
- `assessment_hold_flags`

说明：
- 收口协同只负责提示“还有哪些历史结果、待补学项、待补考项需要处理”
- 不直接操作 `F003` 的账号禁用、权限回收、会话失效逻辑

## 5. 核心流程

### 5.1 生成考核计划

1. 运营选择一个已发布蓝图版本
2. 选择考核场景：模拟考 / 正式考 / 补考 / 复测
3. 选择参与人范围、时间窗、场次模式
4. 系统生成 `assessment_plan`、`assessment_sessions`、`assessment_attempts`
5. 将可提醒的节点派生给 `F018/F019`

### 5.2 执行考核

1. 场次开始前校验参与人与评分人
2. 成员完成客观题或情景演练
3. 系统自动记录客观题得分
4. 评分人补充主观评分与备注
5. 缺考、豁免、异常中止按 `attempt` 状态落档

### 5.3 复核与确认结果

1. 系统汇总客观分、主观分和评分表明细
2. 根据通过线、必达项、异常规则给出结果建议
3. 经理或运营确认最终结论
4. 写入 `assessment_results`
5. 需要认证的写入或更新 `certification_records`

### 5.4 未通过处理与收口协同

1. 未通过或缺考成员进入补学 / 补考判断
2. 生成 `remedial_actions` 或 `resit_recommendations`
3. 若成员状态发生变化，系统生成 `closure_actions`
4. 向 `F003` 发出协同信号，但不直接执行账号处理

## 6. 状态机

### 6.1 考核计划状态

```text
DRAFT -> PUBLISHED -> IN_PROGRESS -> COMPLETED
      \-> CANCELLED
```

说明：
- `PUBLISHED` 后才能派生场次和提醒
- `COMPLETED` 表示该计划下所有 `attempt` 都已结束并确认结果

### 6.2 参与人考核状态

```text
NOT_SCHEDULED -> SCHEDULED -> IN_PROGRESS -> SUBMITTED -> SCORED -> CONFIRMED
               \-> ABSENT
               \-> WAIVED
               \-> CANCELLED
```

说明：
- `SUBMITTED` 表示答题或演练已结束，等待评分
- `SCORED` 表示已出分，仍可能等待人工确认
- `CONFIRMED` 才能写入最终结果归档

### 6.3 认证记录状态

```text
NOT_GRANTED -> PENDING_REVIEW -> GRANTED
            \-> NOT_PASSED
            \-> EXPIRED
```

说明：
- `PENDING_REVIEW` 用于成绩已出但认证结论尚未确认
- `EXPIRED` 用于有效期型认证，不代表历史结果消失

## 7. 默认结构建议

`F026` 先锁执行结构，不锁死最终监考、抽题和发证流程。

### 7.1 默认考核场景
- `SIMULATION`
- `FORMAL`
- `RESIT`
- `RECHECK`

### 7.2 默认评分维度建议
- 产品与方案理解
- 需求澄清与场景判断
- 商务与风险判断
- 沟通表达与应对
- 协同推进与下一步动作

### 7.3 默认异常处置类型
- `ABSENT`
- `WAIVED`
- `INVALIDATED`
- `MANUAL_REVIEW`

## 8. 与其他 REQ 的边界

| 功能 | 拥有者 |
|------|--------|
| 岗位路径、阶段复核、导师反馈 | `F024` |
| 题库对象、题目版本、组卷蓝图 | `F025` |
| 考核计划、场次、评分表、结果归档、认证记录 | `F026` |
| 日程项、提醒规则、提醒发送 | `F018 / F019` |
| 用户禁用、权限回收、会话失效 | `F003` |

这条边界必须稳定。

否则会出现四个常见问题：
1. 把蓝图和考试计划做成同一对象
2. 把考试场次塞进通用日程表里
3. 把评分表当成题库的一部分长期维护
4. 把未通过或离岗收口直接写成账号禁用动作

## 9. 数据建模原则

推荐强类型对象：
- `assessment_plans`
- `assessment_sessions`
- `assessment_attempts`
- `score_sheet_templates`
- `score_sheets`
- `assessment_results`
- `certification_records`
- `closure_actions`

关键原则：

1. **蓝图快照先于计划执行**  
   计划创建时应锁定蓝图版本，避免后续蓝图变更影响已排考核。

2. **计划、场次、参与人分层**  
   计划是运营对象，场次是时间空间对象，`attempt` 是成员执行对象。

3. **评分模板与评分实例分离**  
   模板定义评分结构，实例承接某次具体评分记录。

4. **自动分与人工分分账**  
   客观题自动计分，主观题保留人工录入与复核轨迹。

5. **结果确认先于认证写入**  
   `assessment_results` 确认后，才能更新 `certification_records`。

6. **收口动作只发协同信号**  
   `closure_actions` 只表达待处理事项，不直接替代 `F003` 的账号动作。
