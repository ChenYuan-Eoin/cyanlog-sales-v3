# 顺丰自助下单 PRD v0.4 · 一屏查寄与地址下单

日期：2026-09-11｜F054｜分支：codex/sf-self-service-order
状态：in_progress；WP11；用户已批准开发，代码与隔离验证进行中。

## 1. 已明确的需求
优先解决：用户每天收到地址后，需要在顺丰网页反复切换下单与查询。系统应独立完成「拿到地址 → 确认收件信息 → 下单 → 查运单」，日常流程无需挂着或切回顺丰网页。
新增「自助下单」分页，本期仅开放给用户本人使用。横屏同页左右分栏，右侧运单查询，左侧寄件下单。
右侧以顺丰运单查询业务区域为1:1视觉和交互参考；左侧参照顺丰下单页。各占约一半空间、独立滚动，查询不清空寄件内容。
本期不关联业务订单、报价、合同、客户或CRM；不开发销售多人使用、客户负责人划分及违规下单管控。
未来能力写入PRD并预留少量明确的接入位置；本期不提前实现客户/订单绑定表、复杂配置界面或权限引擎。

## 2. 推荐的最小可用范围
- 复用系统登录，通过服务端可配置的访问名单限制本人使用；其他人不显示入口且接口拒绝访问。无需新账号体系。
- 右侧：输入单个运单号、查询、显示真实状态及物流时间线；分别显示无记录、需验证和查询失败。
- 左侧：寄件姓名/电话/地址、收件姓名/电话/地址、物品、预估重量、已开通的服务和付款方式；常用寄件信息预填。
- 提供「粘贴收件信息」文本框：整段粘贴拿到的姓名、电话和地址，解析回填可编辑字段；缺失或不确定项提示人工确认，不能猜测姓名、地区或门牌。首版不依赖新增付费AI服务。
- 单票确认发单；返回运单号时支持复制及「在右侧查询」。无返回值不伪造成功、费用或物流节点。
- 查询与下单独立保持状态，优先完成用户桌面/横屏路径；窄屏只做基础可用适配。
- 右侧补充本系统最近寄件的简短列表（如最近10票），点击运单即查询，刷新后仍可找到；直接复用最小寄件记录，不扩展完整订单管理。也允许输入其他运单号，在顺丰实际授权范围内查询。
- 本期配置一套已授权顺丰连接及付款方式，使用服务端环境配置，不在页面或代码常量中写死账号、寄件地址或快递服务编码，不新建配置中心界面。

中国大陆普通单包裹、具体结算方式仍为建议；需与真实顺丰账号能力对齐，不要求为了本工具先建设公司月结管理。
「1:1」不能通过缩小范围自动取消：开发前先采集实际页面参考。若半屏宽度与原站布局冲突，以同等宽度截图验收，布局取舍与用户确认。

## 3. 从本期移出的功能
后台账号/部门管理、客户负责人分配、违规审批、费用统计/对账、批量寄件、面单打印、后台物流推送、完整寄件记录列表、系统内取消、数据库草稿管理、资料保留策略自动化。
取消或售后暂用顺丰官方渠道；此为推荐精简方案，不把系统内取消悄悄算入两小时目标。
日后面向销售时再做：登录用户 → 客户负责人 → 客户 → 业务订单/寄件记录；负责人调整保留历史责任人。
销售系统身份与顺丰结算账号分别设计，是否一人一月结账号以后决定。

## 4. 必须保留的最小可靠性
仅本人可用不等于接口可公开；复用已有服务端认证和可配置访问名单；仅隐藏菜单不足以控制访问。
顺丰密钥留在服务端，电话地址不打印到普通日志，浏览器不保存顺丰密钥。
发单确认、提交锁定、服务端幂等保护；超时后以同一内部请求号查回，结果未明时不得新建请求重发。
「不绑定业务订单」与「不记录发单请求」不同：只保留防重及恢复需要的最小寄件尝试记录，不建设业务订单中心。
建议一张最小记录表：请求ID、创建人、幂等键、提交状态、顺丰运单号、时间；必要的请求摘要用于一致性校验，不复制客户域。
进程内Map或只禁用按钮不能防止刷新、重启及多实例重复发单，因此不能作为真实发单的唯一保护。
不用新增定时任务；待确认请求由本人重新查询触发恢复。上游受理但本地更新失败时也用原请求ID查回。

### 后续扩展位置（本期只保留接口边界）
1. 访问策略：入口与API读取同一份服务端访问配置。先只配置本人，以后扩展为销售角色/授权名单，不改寄件页面。
2. 下单校验：所有发单经过统一服务端校验入口；当前只校验身份、字段、账号可用性及防重，以后可接入业务订单是否存在、状态是否允许、客户负责人是否匹配等规则。不可把“允许自由寄件”散落在页面中。
3. 来源信息：创建寄件的输入预留可选来源描述，当前只有manual，无业务订单依赖。未来order来源须服务端查询订单并验证，客户端自报订单号不算授权。本期拒绝未实现的来源类型，新增字段及迁移在开发该能力时完成。
4. 物流适配：顺丰调用集中在一处，页面消费统一的下单/查询结果，结算配置与业务策略分别处理。
5. 未来策略启用后，必须在服务端约束是否仍允许manual；不能只隐藏自由寄件按钮，否则可绕过按订单下单要求。
本期不实现规则编辑器、多人客户归属、订单校验策略或多快递平台；上述边界是避免重写的最小结构。

## 5. 接入路径选择
A. 原生双栏 + 官方API（推荐）：符合站内真实查件/下单，账号就绪后只做最小接口与单票流程。
B. 双栏嵌入顺丰官网：只在官方允许嵌入且登录/验证码在本系统内可用时考虑；当前未验证，不以iframe两行代码作为工期承诺，不绕过官网限制。
C. 跳转顺丰官方页面：最快可提供入口，但不满足同屏站内操作，只能作为用户接受的临时替代，不能声称需求完成。
当前分支代码检索未发现sf-express/sfapi/顺丰接入实现；仅证明本次检索范围无匹配，不证明企业没有外部顺丰账号。
官方接入说明确认需注册、配置接口和测试；用户是否已有可用应用及下单/轨迹/结果查询权限仍未知。

## 6. 开发路径及时间判断
先做15–30分钟接入预检：确认可用账号与权限、沙盒连通、真实页面参考及现有认证/存储复用点。此为建议时间预算，不是已执行结果。
预检通过后按一个个人寄件任务实现：双栏页面与地址粘贴回填 → 最小下单/轨迹/结果查询适配 → 防重存储与最近寄件 → 一屏完整路径回归。
不按几天日程排满，也不再拆出多个管理子系统。

| 环节 | 初步投入预算 | 输出 |
|---|---|---|
| 接入及页面预检 | 15–30分钟 | 明确接口可用性、参考页和阻断 |
| 双栏UI与表单 | 45–75分钟 | 左下单右查询的可操作页面 |
| 接口、最小存储及防重 | 60–120分钟 | 沙盒真实发单、查件及超时查回 |
| 目标回归与修正 | 30–60分钟 | 成功、错误、重复提交、非本人访问验证 |

以上为工程判断，合计约2.5–5小时，不是测量数据或交付承诺；依赖就绪时两小时可作为首轮交付检查点，仍有机会更快完成。不能把该检查点自动等同于生产已可用。
本次补充地址解析回填及最近寄件，纳入首轮工作而非遗漏项；解析异常以人工校正收敛，不建设通用地址识别平台。此前估算仍为粗估，需预检后按实测修正。
两小时适合交付双栏可操作版本；如果接口现成可用且联调顺利，争取接通真实沙盒闭环。接口未开通时展示明确未接通状态，不用模拟结果冒充。
账号申请/权限开通属于外部等待，单列状态，不折算成连续开发工日。
上线另计既有集成检查、部署与线上验证的实际耗时，先执行再记录，不把整个项目历史阻断估成该页面开发量。
旧版3–5工作日估算作废：它混入了多人平台、配置后台、取消、完整记录与发布流程，且没有测量支撑。

## 7. 最小验收
1. 本人可见并使用；未登录和其他账号不能调用接口。
2. 同屏左寄右查，分别滚动；查询及查询报错不丢左侧输入。
3. 有效运单展示真实轨迹；无记录/需验证/无权限/失败如实显示。
4. 粘贴一段姓名/电话/地址后正确回填；缺失、不确定、多个收件人等输入必须提示确认，允许手工修正；确认一票寄件后得到真实运单，可复制或在右侧查询。
5. 双击、刷新重试不会产生第二张有效寄件单；发单结果不明时保留原请求ID供查回。
6. 下单字段错误可修正，密钥不出现在客户端及日志。
7. 下单后刷新可从最近寄件找到运单并查轨迹，整条日常操作链不要求打开顺丰网页。地址解析及查询不影响其他表单状态。
8. 用户范围通过配置开放；未实现的订单来源被拒绝，现有发单入口统一经过服务端校验。
9. 既有登录和主要导航通过目标回归。按仓库要求在集成/发布阶段补齐对应检查。
10. 生产验收需单独确认真实寄件资料及运费安排；沙盒成功不写成线上已更新。
