## 1. 这份 Packet 解决什么问题

这不是一个独立交付 REQ，而是配置中心的共享架构真相。

它用于约束以下功能包：
- `F001` 价盘与阶梯价
- `F009` 合同审核规则配置
- `F010` 报价规则配置
- `F011` 组织权限配置
- `F012` AI 运行时配置

同时它约束这些消费方：
- `F002` 报价编制
- `F004` 审批流执行
- `F005` 合同审核
- `F006` 规则执行内核

如果没有这份共享架构，单个 F 文档很容易退化成“某个页面的 CRUD 说明”，最终把“配置中心”做成“几个 Tab 的集合”，丢掉真正的所有权边界。

---

## 2. 三层架构

配置中心必须严格按三层理解和落地：

| 层级 | 含义 | 谁可写 | 谁消费 |
|------|------|--------|--------|
| 第一层：可配置能力域 | 系统允许配置什么 | 配置中心管理员 | 各业务模块 |
| 第二层：模块具体配置 | 每个能力域下具体有哪些配置项、版本、生效规则 | 配置中心管理员 | 各业务模块 |
| 第三层：业务工作区域 | 业务页面如何读取并使用配置 | 业务用户写业务数据，不写配置 | 报价、合同、审批等页面 |

**强约束**：
- 业务页面只能消费配置，不能修改配置
- 配置修改、发布、回滚只能在配置中心完成
- 配置中心是控制面，业务中心是执行面

## 3. 能力域拆分

| 能力域 | Active Packet | 配置拥有权 | 主要消费方 |
|--------|---------------|------------|-----------|
| 价盘与阶梯价 | `F001` | 配置中心 | `F002` |

| 组织权限 | `F011` | 配置中心 | `F003`、`F004`、全局导航 |

这里的拆分不是按页面拆，而是按“配置拥有权”和“消费边界”拆。

## 4. 正确的配置中心形态

配置中心不是“一个大列表页 + 若干静态卡片”。

正确形态应当是：
1. 左侧先选能力域
2. 中间进入该能力域的配置集合
3. 右侧或详情面板维护具体配置项、版本、生效状态、测试结果
4. 业务页面只显示“当前命中的配置结果”，不暴露配置写入口

因此，配置中心 UI 可以有 Tab，但 Tab 不能代替领域模型。

布局必须服务两个目标：信息密度高、逻辑与操作闭环清晰。三栏只适用于树、列表、当前对象需要同时可见的领域，不能成为固定页面模板。AI 平台采用“任务导航 + 当前任务工作区 + 独立发布检查”；iPad 下保持单列任务顺序。任何布局都不得用异高 Grid stretch、CSS masonry 或 `columns` 掩盖结构问题。闭环区需要显示影响范围、发布状态、阻断原因、下一步动作和版本入口；若只重复主区信息或把少量信息做成大卡片，应判定为不合格。

| 栏位 | 配置中心职责 | 合格表现 |
|------|--------------|----------|
| 导航区 | 能力域 / 规则集 / 组织树 / 当前任务 | 高密度树、列表或有序任务，带数量、状态、异常提示 |
| 工作区 | 当前对象集合与主要编辑区 | 可浏览、搜索、筛选、编辑、测试，不把全部任务同时展开 |
| 闭环区 | 发布闭环、影响范围、证据与下一步动作 | 能回答“当前配置是否可用、影响谁、下一步做什么”；可按屏宽独立或落在工作区下方 |

### 4.1 组织与权限是独立控制面

配置中心内部至少应稳定成以下信息架构：

- `交易配置`
  - 价盘与阶梯价
  - 税率规则
  - 审批参数
- `合同规则`
  - 合同审核规则
- `AI 平台`
  - 模型接入
  - 模型目录
  - AI 应用与路由
  - 业务用点与绑定
  - 发布状态
- `组织与权限`
  - 组织架构
  - 角色权限
- `界面与体验`
  - 主题与品牌

`界面与体验` 下必须拆分 `BrandProfile` 和 `ThemeRelease`：品牌负责产品名、侧边栏 logo、浏览器 favicon、Word 批注作者展示；主题负责颜色、组件变量和布局密度。运行时只能消费一个 active/published 品牌版本和一个 active/published 主题版本，不能让 favicon、侧边栏 logo 和页面名称分别来自不同临时配置。

这里尤其要避免一个常见错误：

**不能把“组织架构 / 角色权限”挂到“合同审核规则”或泛治理分组下面。**

因为：
- 组织架构是审批链、数据范围、导航权限的基础层
- 合同审核规则只是其中一个业务规则域
- 两者不是上下级关系

## 5. 数据建模约束

### 5.1 优先强类型表

以下内容优先使用强类型表或强类型对象，而不是混进一个万能 `configs` 表：
- SKU / 阶梯价
- 合同规则 / 规则版本 / 规则测试记录
- 税率规则 / 折扣矩阵 / 审批流参数
- 组织架构 / 角色 / 数据权限
- AI ProviderConnection / ModelCatalogEntry / AIApplication / BusinessUsePoint / ApplicationBinding / RoutePolicy
- BrandProfile / ThemeRelease / FaviconAsset

### 5.2 泛型配置只做低频策略

泛型 `configs` 只能用于：
- 低频、弱结构、变化快的策略项
- 明确不值得单独建模的辅助配置

**禁止**把整个配置中心都压到一个 `configs` 表里，然后靠 `type + jsonb` 承载所有能力域。这样会直接抹平领域边界，也会让版本、生效、校验、权限控制一起变形。

WP01 允许一个明确的可回滚过渡：在不写 Production、不做不可逆迁移的前提下，六个 AI 对象暂时“一行一个严格 discriminated 对象”存入既有 `configs`。它不是把六对象聚合成一个万能 JSON 图；类型、稳定身份、引用、发布和 UI 都必须独立。

该过渡不自动获得“安全可发布”结论：草稿 probe 只是当次参数探测，不持久化生产健康状态。隔离 Preview `vsfropnfsmnonkotywsx` 已应用 `secure_ai_config_control_plane` 迁移并通过动态 bearer canary，证明 Preview 当前记录可持有凭据而 `config_versions` 不保留该凭据；此结论不外推到 Production。通用 `configs` 的切换仍不是数据库原子事务。Production 切换前，WP09 须在隔离 Preview 验收专用事务/RPC 或强类型表方案。

## 6. 发布、生效、回滚

所有配置能力域都需要统一具备以下机制：

| 能力 | 说明 |
|------|------|
| 草稿态 | 编辑中，不影响线上业务 |
| 发布态 | 业务消费方只能读取已发布版本 |
| 生效控制 | 支持立即生效，必要时支持定时生效 |
| 版本历史 | 每次变更可追溯 |
| 回滚 | 可切回历史发布版本 |
| 审计 | 记录谁在何时修改了什么 |

MVP 可以先简化 UI，但不能跳过这些语义。

## 7. 消费侧约束

### 7.1 报价中心
- 读取 `F001` 的 SKU / 阶梯价
- 读取 `F010` 的税率、折扣矩阵、审批流参数
- 读取 `F011` 的审批权限、数据范围
- 自身只写报价快照，不回写配置

### 7.2 AI 业务消费方
- 读取 `F009` 的结构化规则、语义规则、消息模板
- 业务代码注册 `F012 BusinessUsePoint`，只绑定已发布 `AIApplication`
- `AIApplication → RoutePolicy → ModelCatalogEntry → ProviderConnection` 决定模型和降级
- 合同审核、起草、标书等业务自身只写业务结果和调用审计，不直接绑定 Provider、模型或回写平台配置

### 7.3 Account / 全局导航
- 读取 `F011` 的角色、菜单权限、数据范围
- `F003` 负责认证、会话、鉴权执行，不拥有组织配置的编辑权

## 8. 反模式清单

以下做法视为偏离真相：
- 把配置中心做成“一个页面里几套彼此无关的 CRUD”
- 在报价页、合同页直接修改配置数据
- 用一个泛型 `configs` 表吞掉全部能力域
- 把“规则执行”和“规则配置”写进同一个 F 包里
- 把“鉴权执行”和“组织权限配置”混成同一层
