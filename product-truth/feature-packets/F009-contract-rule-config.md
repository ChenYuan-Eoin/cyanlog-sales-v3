# F009 合同审核规则管理

**状态**：当前产品真相

**所属业务模块**：合同审核

**上游**：配置中心、组织权限

**下游**：F006 合同审核运行时、ReviewRun、风险处理与批注输出
**最后校准**：2026-07-20

## 1. 产品目标

F009 管理的是“合同审核依据”，不是 Prompt、模型参数或机器字段。

用户应当能够像在 Jira / ONES 中管理工作项一样，从规则集合逐层进入明确对象：

`规则集 → 问题分类 → 具体规则 → 规则详情 → 业务属性 → 判定与处理`

例如“合同金额不得低于 5 万元”是一条规则；“合同金额”是这条规则的金额属性；`金额 < 50000 CNY` 是判定条件；“阻断并要求修改”是处理方式。配置阶段不存在“先留空、运行时再提取属性”的产品逻辑。

## 2. 与平台 AI 的边界

AI 模型是平台能力，合同审核只是消费者之一。模型接入、可用模型、模型探测、路由和降级属于 F012，不属于规则详情。

F009 当前只服务 `contract_review`。界面固定显示“合同审核”，不提供运行时无法执行的自由文本场景配置。以后其它业务模块接入规则能力时，由该业务模块选择自己的规则资产，并同时提供可审计的消费上下文；不能靠单条规则中的模糊场景词假装隔离。

AI 在规则运行期只有两项职责：

1. 在合同原文中定位与已发布规则相关的连续原文；
2. 按规则预先定义的属性类型读取值、单位、证据和置信度。

AI 不得创建属性、改写条件、选择风险结果或覆盖处理动作。服务端验证原文证据、类型和单位后，使用已发布判定条件确定性计算结果。

## 3. 配置对象

### 3.1 规则集

规则集是版本和发布的原子边界，负责：

- 名称、编码和维护说明；
- 所含规则；
- 当前线上版本与待发布版本；
- 统一测试矩阵、发布和历史快照。

规则集不负责定义模型，也不把问题分类、金额或时限混为同一级标签。

### 3.2 问题分类

问题分类用于组织业务问题，例如：

- 付款与结算；
- 验收与交付；
- 违约与赔偿；
- 知识产权；
- 数据安全。

分类是导航和治理对象，不参与替代具体规则。分类名称、说明和当时含义必须随发布证据冻结，避免历史审核的分类语义漂移。

### 3.3 具体规则

每条规则至少包含：

- 稳定编码、名称和业务说明；
- 所属规则集和问题分类；
- 组织作用域、优先级、启用状态；
- `rule_contract v1` 规则详情。

旧 `engine_type`、`target_field`、`field_hints`、`semantic_prompt` 和 Level A/B/C 列仅供历史兼容适配，不是新规则配置协议，也不得成为发布完整性的替代证明。

### 3.4 业务属性

属性是规则详情最末端、最直接的通用能力。一条规则可以有多个属性。

| 类型 | 示例 | 必须配置 |
|---|---|---|
| 金额 | 合同金额 50000 CNY | 币种 |
| 比例 | 首付款比例 30% | `percent` |
| 时限 | 验收后 30 天 | `day/month/year` |
| 日期 | 2026-08-01 | ISO 日期 |
| 枚举 | 付款方式=银行转账 | 明确选项 |
| 是/否 | 是否允许转包 | 布尔值 |
| 文本 | 管辖地包含“上海” | 包含或存在性语义 |
| 数字 | 交付批次 3 | 可选业务单位 |

属性名、类型、单位、是否必填和枚举选项均由规则作者明确配置。运行时的“读取”不反向修改这些配置。

### 3.5 判定与处理

每条判定包含：

- 稳定判定 ID 和用户可读名称；
- 优先级，数字越大越先判断；
- `all` / `any` 条件组合；
- 结果：通过、需谈判、阻断、人工复核；
- 处理动作；
- 用户说明/批注意图。

服务端按优先级确定第一条命中判定；风险严重度不能暗中覆盖作者明确设置的优先级。缺少必填属性、同文多值、币种冲突或没有可达判定时，按 `missing_evidence_outcome` 转人工复核或阻断，绝不默认通过。

## 4. 生命周期

### 4.1 保存草稿

保存必须在一个事务内完成：

1. 锁定规则集，再锁定规则；
2. 合并并校验完整业务字段；
3. 生成单调递增、不可复用的规则版本；
4. 写入 live 草稿和对应 `RuleSnapshot(draft)`；
5. 将所属规则集标记为待发布；
6. 记录操作者和内容哈希。

草稿不会改变当前线上规则集快照。

### 4.2 停用

停用是“下一规则集版本移除该规则”的草稿动作。当前线上审核继续使用旧发布快照，直到规则集重新发布。删除或停用不得直接抹去历史快照。

### 4.3 测试矩阵

规则当前草稿版本必须通过：

- 每一条判定各一例，精确命中目标 decision ID；
- 缺少证据；
- 非文本属性的同文多值冲突；
- 金额属性的币种冲突。

测试记录必须绑定规则草稿快照/规则合同哈希和 evaluator revision。相同测试目标只认最新一次运行；后续失败必须撤销之前的通过状态。

### 4.4 规则集发布

发布以规则集为唯一原子边界：

1. 锁定规则集和全部成员规则；
2. 验证 canonical 配置和最新测试矩阵；
3. 从验收通过的草稿只追加一份不可变的已发布规则快照；
4. 生成新的不可变 `RuleSetSnapshot`，冻结精确 `rule_snapshot_ids`、分类语义、参考文档 ID、测试证据和发布人；
5. 原子切换规则集唯一 `current_snapshot_id` 指针，旧快照保持原样作为历史证据；
6. 让 F006 只从该当前 RuleSetSnapshot 编译 SkillBundle。

单条 canonical 规则发布、回滚或 AI 转译写入都不得绕过该边界。

## 5. 正式审核运行合同

正式审核只读取当前 `RuleSetSnapshot` 指向的精确规则快照，不读取 live 草稿，也不按“看起来已启用”猜测线上状态。

运行链为：

`合同原文 → 已发布规则集成员 → AI/确定性定位属性证据 → 服务端校验 typed readings → 确定性判定 → 已配置处理动作和用户说明 → RiskFinding / 批注 → ReviewRun 证据`

AI 输出至少包含规则编码/版本、每个属性的 key、状态、typed value、unit、连续原文 evidence 和 confidence。服务端负责：

- 证据确实存在于本次合同原文；
- 属性属于该规则且类型、枚举和单位合法；
- 缺失、歧义和单位冲突不能被伪装为读取成功；
- outcome、risk level、decision ID、标题、说明和动作来自已发布规则，而非模型自由文案。

控制面查询失败、快照缺失或成员快照损坏必须形成明确阻断/降级证据，不能静默变成“0 条风险”。

## 6. 历史审计

一次 ReviewRun 必须绑定：

- 合同源版本；
- RuleSetSnapshot / RuleSnapshot IDs；
- SkillBundle；
- 模型策略及真实 model invocation；
- token、provider、model、延迟与降级信息；
- 风险的 decision ID、属性 readings 和连续原文证据。

后续发布不得修改旧的已发布快照；“当前版本”只由规则集唯一 `current_snapshot_id` 指针表达。历史 ReviewRun 对显式绑定的非当前快照仍必须可回放；早期遗留的 `rolled_back` 已发布证据继续兼容，但 `draft` 永远不能作为正式历史证据。

## 7. 页面信息架构

配置中心采用三层主导航，而不是机器字段堆叠：

1. 规则集：线上版本、草稿版本、规则数、测试完成度、发布阻断；
2. 问题分类：分类名称、说明、规则数量；
3. 规则列表与详情：基本信息、属性、判定与处理、输出、逐项测试。

页面必须同时显示“当前线上版本”和“正在编辑的草稿版本”。“已保存”“已测试”“已发布”“已被正式审核消费”是四个不同事实。

## 8. 数据真相

主要实体：

- `contract_rule_sets`
- `contract_rule_problem_categories`
- `contract_rules_v2`
- `contract_rule_snapshots`
- `contract_rule_test_runs`
- `contract_rule_set_snapshots`
- `contract_rule_set_documents`（可选参考，不是发布前置条件）

运行时真相是发布快照，不是表单、环境变量、旧配置列或外部 GitHub skill。Production 数据迁移和发布需单独批准；Preview 可用于隔离验证。

## 9. 第一阶段验收

- 能从规则集进入分类、规则和规则详情，不出现“属性提取/AI 转译”配置入口；
- 金额、比例、时限、日期、枚举、布尔、文本、数字矩阵与实际运行一致；
- 多属性、多判定规则可逐条完成测试，失败重测会撤销旧通过；
- 草稿保存/停用不影响线上审核；规则集发布后才切换；
- AI 同义表达定位可生成合法 typed reading，最终判定和处理仍由服务端规则决定；
- 控制面故障 fail closed；
- 新旧 ReviewRun 都可按绑定快照回放；
- 没有任何预置规则的新组织可以只用业务名称和表单完成规则集、问题分类、规则、属性、条件与处理配置；内部编码由系统生成；
- API、类型检查、构建、桌面与 iPad 浏览器、真实合同运行证据全部通过。

## 10. 历史兼容边界

已有 Level A/B/C 和机器字段由单向 legacy adapter 保持历史审核可回放。它只能是迁移桥：R001–R015 作为可编辑预置草稿展示，组织保存后形成 canonical `rule_contract v1`，完成新测试矩阵并随规则集主动发布。预置数据不是平台真相、不是用户确认门，也不得自动生效；兼容成功不等于新配置已经完成。
